# 终端附着与控制台日志

> 状态：**已落码**。由 AI 起草并实现，人工审定。  
> 日期：2026-10-26  
> 关联：`backend/src/console.rs`（新增）、`backend/src/main.rs`、`backend/src/cli.rs`、`backend/src/config/logger.rs`

---

## 1. 结论先说

1. 两条需求同时成立、互不冲突：**双击 / 自启动零控制台**，**终端里启动时日志进当前终端**。代价是必须放弃「shell 等待进程」。
2. release 继续用 **GUI 子系统**（`windows_subsystem = "windows"` 不动）。终端里能看见日志靠两件事，**缺一不可**：
   1. `AttachConsole(ATTACH_PARENT_PROCESS)` 附着父进程已有的控制台；
   2. 附着后重新打开 `CONOUT$` 并 `SetStdHandle` 重绑 `stdout` / `stderr`。  
      只做第 1 步（旧 `cli.rs::attach_parent_console`）时能出字纯属巧合——句柄恰好被父进程继承下来。
3. Ctrl+C 从「内核直接结算、退出码 `0xC000013A`」改为「跑完退出钩子 → `exit(0)`」。
4. **只有 Windows 需要「附着」**。Unix 没有子系统、也没有控制台句柄，进程直接继承 0/1/2。
5. 已知限制：Git Bash / mintty 没有 Win32 控制台，附着落空（见 §6）。
6. **接管终端是显式开关**（2026-10-27 起）：`ROLLCALLER_ATTACH_CONSOLE_ON_WIN32` 为真值时，
   从终端启动的 GUI 才会附着；默认不附着，日志只进文件。CLI 命令不受开关限制（见 §11）。

---

## 2. 为什么不能改用 console 子系统

Windows 上「子系统」这一个 PE 头字段同时决定了三件事：进程创建时**是否自动附着父进程的控制台**、`cmd` / PowerShell **是否等待**它退出、Explorer 启动时**是否给它新建一个控制台窗口**。三者不可分开设置。

| 方案                                    | 双击启动                     | 终端里启动   | shell 是否等待             |
| :------------------------------------ | :----------------------- | :------ | :--------------------- |
| **A. GUI 子系统 + 附着**（已采用）              | 无控制台 ✔                   | 日志进终端 ✔ | **否**，提示符立刻回来，日志与提示符交织 |
| B. console 子系统 + 无父控制台时 `FreeConsole` | **闪一帧黑窗**（窗口由系统在进程入口前创建） | 日志进终端 ✔ | 是，行为最像 CLI 工具          |

用户裁定（2026-10-26）：release **绝不允许每次启动闪黑窗**，因此选 A。终端里的日志属调试用途，提示符与日志交织可以接受——VS Code、Chrome 在 Windows 上是同一套行为。

实际观感（探针实测）：附着后进程持续打印 5 秒，而 oh-my-posh 提示符在这 5 秒内就已经画出来了；一旦在提示符上回车，shell 会重绘当前行，把它下方的残留日志行抹掉。**这是预期内的**，不是丢日志。

## 3. 判定顺序（`console.rs`）

状态只有三个，进程内只判定一次（`OnceLock`），`main` 第一行完成：

| 状态           | 含义                                         | 影响                            |
| :----------- | :----------------------------------------- | :---------------------------- |
| `Attached`   | 持有真正的控制台                                   | 挂控制台日志层；ANSI 可用；Ctrl+C 会送达本进程 |
| `Redirected` | stdout 被重定向到文件 / 管道（`> out.txt`、`\| more`） | 挂控制台日志层但**关 ANSI**            |
| `Detached`   | 没有任何输出通道（双击、自启动、服务）                        | **整层不挂**：省掉格式化与必然失败的写入        |

判定顺序（顺序本身是契约）：

1. `GetConsoleMode(stdout)` 成功 ⇒ 已附着（debug / develop 是 console 子系统，创建即附着），只需补开虚拟终端处理；
2. 否则 `GetFileType(stdout)` ∈ {`FILE_TYPE_DISK`, `FILE_TYPE_PIPE`} ⇒ `Redirected`，**绝不 `AttachConsole`**——那会把用户的重定向从文件 / 管道抢回控制台；
3. 否则看开关：`ROLLCALLER_ATTACH_CONSOLE_ON_WIN32` 非真值 ⇒ `Detached`（**默认路径**，根本不调 `AttachConsole`）；
4. 否则 `AttachConsole(ATTACH_PARENT_PROCESS)`：失败 ⇒ `Detached`；成功 ⇒ 打开 `CONOUT$`、重绑两个标准句柄、开 VT ⇒ `Attached`。

三条硬约束：

- **不 `AllocConsole`**：那会在双击启动时凭空弹出黑窗，正是方案 A 要避免的；
- **`CONOUT$` 的 `File` 必须活到进程结束**（存进 `static`）：`File` 一 drop，刚绑上去的句柄立即失效；
- **重定向优先于附着**：判定 2 必须先于判定 3 / 4，否则 `rollcaller.exe -v > a.txt` 会写到屏幕上而不是文件里。

Unix 侧没有这些概念：stdout 连终端 ⇒ `Attached`，否则 `Redirected`（桌面图标启动时指向 `/dev/null`，空写无害，换来重定向仍有输出）。`Detached` 在 Unix 上不会出现。

## 4. 与 `logger` / `cli` 的契约

- `main` 的调用顺序是契约：`cli::handle_cli_args()` → `console::attach()` → `run()`。
  CLI 命中会在中途 `exit`，所以两个附着入口**互斥**：CLI 走 `attach_for_cli()`（无条件），GUI 走 `attach()`（看开关）。
- `console::attach()` **必须早于任何输出**：`bootstrap` 的目录 `info!`、`logger` 的挂载判断都读它的结果。
- `logger::build()` 用 `console::has_output()` 决定**是否挂控制台层**，用 `console::ansi_enabled()` 决定 `with_ansi`（真控制台 + `NO_COLOR` 非空 / `TERM=dumb` 之外）。文件层与 JSON 遥测层不受影响。
- 控制台与文件层共用 `LogFormat`（自定义 `FormatEvent`），行形与 `scripts/common/logger.py` 对齐：
  `<ISO8601 三位小数> [WARNING]  <crate> <file:line>: <正文>`。级别名按 Python 口径（`WARN` → `WARNING`），
  `target` 只保留 crate 段，依赖的 `.cargo/registry` 前缀裁到 `crate-version/src/…`；线程只写名字，不带 `ThreadId`。
- `cli.rs` 只负责触发附着（`attach_for_cli`）与打印，不再自己调 `AttachConsole`。

副产品（无需额外实现）：`-v | more`、`-v > a.txt` 这类重定向终于正确（旧实现依赖句柄继承）；`show_fatal_error` 的 `eprintln!` 在终端里可见。

## 5. Ctrl+C：`0xC000013A` 与 `exit(0)` 的区别

默认情况下，终端里的 Ctrl+C 由**内核**按默认方式结算进程：进程被直接终止，退出码 `0xC000013A`（`STATUS_CONTROL_C_EXIT`）。此时数据库连接池不会关、`shutdown_hooks` 不会跑。

现在注册 `SetConsoleCtrlHandler`，只接管 `CTRL_C_EVENT` / `CTRL_BREAK_EVENT`：

```
回调（系统线程，立刻返回 TRUE）
  └─ 独立线程：tracing::info! → shutdown_hooks::finish_and_exit(0)（清理钩子 → 看门狗 → exit(0)）
       └─ 第二次 Ctrl+C：跳过收尾，直接 exit(0)
```

与更新安装链路（`service/update/install.rs`）同一套退出语义：钩子跑完直接退出。`CTRL_CLOSE` / `LOGOFF` / `SHUTDOWN` 不接管——系统只给 5 秒，抢不过，交回默认处理。

**必须说清的一点**：Ctrl+C 是**广播**，同一控制台里每个附着进程各收一次。所以下面这些**不会**因为改成 `exit(0)` 而消失：

```
^CTerminate batch job (Y/N)?          ← cmd.exe 在跑 .cmd shim（pnpm / npm）时的提示
[WARNING] [util/sigint.py:33] 执行 Ctrl+C，正在退出...   ← dev.py 自己的 handler
error: recipe `dev` failed on line 27 with exit code 1   ← just 对子进程退出码的汇报
```

它们分别属于 cmd、`dev.py`、`just`，只有 `error: process didn't exit successfully ... (exit code: 0xc000013a)` 这一行是我们自己的、会随 `exit(0)` 变成正常退出。在 release 里直接 `.\rollcaller.exe` 时，链上只有 PowerShell 一个，最多看到 `^C` 前缀。

Unix 侧不接管 SIGINT：信号处理器里不能安全地 await 清理（异步信号安全），默认的「终止 + 退出码 130」正是 shell 的期待。

## 7. 实测与验证

探针（`#![windows_subsystem = "windows"]`，raw FFI、无依赖）在 Windows Terminal + PowerShell 7 下：

```
[probe] 附着前已持有控制台=false stdout类型=0 AttachConsole成功=true 重绑CONOUT$=true
[probe] ANSI 颜色: 绿 红 黄粗          （三色均正确渲染）
[probe] tick 1/5 … tick 5/5            （提示符在 tick 1 之后即出现 ⇒ shell 不等待）
```

另实测：GUI 子系统进程在 std 句柄为 `NULL` 时 `println!` **静默 no-op、不 panic**（std 把它当「没有输出目标」）。这条结论让「启动早期直接 `println!` 诊断」不至于崩溃，但它不是方案——`bootstrap::init()` 原先的 8 行目录回显已随「日志提前」一并移除（见 §10）。

单测（`cargo test --lib -- console`，6 条）覆盖：`classify` 的四条路径（已附着优先、重定向不可被附着覆盖、
无控制台即 `Detached`、三态语义）+ 开关真值表（`0` / `false` / `off` / 空为假，其余为真）。

注意：AI 侧的 Bash / PowerShell 工具**没有真控制台**（stdout 是管道、`GetConsoleProcessList = 0`），附着分支只能由人在真终端里验证。

## 8. 逃生口

- **想在终端里看日志**：`$env:ROLLCALLER_ATTACH_CONSOLE_ON_WIN32=1`（或 `set ROLLCALLER_ATTACH_CONSOLE_ON_WIN32=1`）后再启动，见 §11。
- 想让 shell 等待：`.\rollcaller.exe | Out-Host`（stdout 成管道 ⇒ 走 `Redirected` 分支、不附着；PowerShell 会等进程退出，日志经管道回显）或 `Start-Process -Wait`。
- 想留痕：`.\rollcaller.exe > run.log`（同上，不走控制台）。
- 不想要颜色：`$env:NO_COLOR=1` 或 `$env:TERM="dumb"`。

---

## 9. 不要做

1. 不要 `AllocConsole`——双击启动会弹黑窗；
2. 不要为了「shell 等待」把 `windows_subsystem` 改回 `console`；
3. 不要在 `console::attach()` 之前输出（那时通道还没重绑）；
4. 不要只 `AttachConsole` 而不重绑 `CONOUT$`（旧实现的做法，靠句柄继承的运气）；
5. 不要把 `Redirected` 判在 `AttachConsole` 之后（会抢走用户的重定向）；
6. 不要在 `logger::init()` 之前用裸 `println!` 写诊断——日志已经提前到  
   `bootstrap::init()` 第一行（见 §10），路径快照走 `debug!`。

## 10. 启动日志顺序（2026-10-26 调整，分支 `refactor/startup-logging`）

原来的顺序是 `ensure_directories → 数据目录写权限探针 → logger::init`，于是「logger 之前」的一切输出只能裸写，`bootstrap::init()` 里积了 8 行 `println!`（`root dir = …`）。

根因不是输出难看，而是**日志起得太晚**：目录不可写这一最常见的启动故障发生时，`show_fatal_error` 里的 `tracing::error!` 是**空的**（订阅器还没装上），只剩 `eprintln!` 与 fatal 文件兜底。

现在的顺序与契约：

1. `logger::init()` 提到 `bootstrap::init()` 第一行；
2. `logger::build()` **永不 panic**：文件层 / 遥测层建不出来（目录不可写、磁盘满）时降级为「只输出到控制台」，用一次裸 `eprintln!` 提示——此刻订阅器还没装上，这条提示只能这样出去。原来的 `expect("Failed to initialize rolling file appender.")` 去掉；
3. 8 行 `println!` 换成一行 `debug!`（内容 = `serde_json::to_string(app_paths::paths())`，与 `--app-paths` 同形）：debug 构建看得见，release 终端默认静默，需要时用 `--app-paths`；
4. 之后的 `ensure_directories` 仍会逐目录 `info!("目录已就绪: …")`（console 层 INFO 起可见）。

## 11. 接管终端改成显式开关（2026-10-27，分支 `feat/console-attach-opt-in`）

### 为什么默认关

附着之后进程和终端是一条绳上的：**关掉终端会收到 `CTRL_CLOSE_EVENT` 被杀，终端里按 Ctrl+C 也会终止它**。
用户双击 / 从任务栏启动的进程，不该因为「某个终端恰好开着」而被绑上去；而「在终端里看日志」是排障需求，
不是日常路径。所以默认关闭，用环境变量显式打开。

### 变量与语义

`ROLLCALLER_ATTACH_CONSOLE_ON_WIN32`（`console::ATTACH_ENV`，帮助文本里有，测试锁住两者一致）

| 值                                                    | 结果 |
| :--------------------------------------------------- | :-- |
| 未设置                                                  | 关   |
| 空串（`set ROLLCALLER_ATTACH_CONSOLE_ON_WIN32=`）        | 关   |
| `0` / `false` / `off`（大小写、首尾空白不敏感）                   | 关   |
| 其余任何值（`1` `true` `on` `yes` `abc` …）                 | 开   |

空串算假是刻意的：批处理里「设了但忘了给值」太常见；falsy 列表还让包装脚本能用 `=0` 临时关掉而不用 unset。

### 生效边界

开关只 gate「要不要调用 `AttachConsole`」这一个动作：

| 场景                                | 结果                    | 看开关吗                  |
| :-------------------------------- | :-------------------- | :-------------------- |
| debug / develop（console 子系统）     | `Attached`            | 不看：创建即附着，`tauri dev` 必须有日志 |
| 重定向（`> a.txt`、`\| more`）          | `Redirected`          | 不看：用户已指定输出目标          |
| release + 终端 + 开关开               | `Attached`            | 开                     |
| release + 终端 + 开关关（默认）           | `Detached`            | 关                     |
| 任何 CLI 命令 / 用法错误                   | 强制附着                  | 不看：见下                 |

### CLI 例外（不可让步）

`-v` / `--build-info` / `--app-paths` / `--mode` / `--doctor` / `-h` 以及用法错误，在 release 下若跟着开关走，
会**静默无输出**（stdout 是无效句柄，写入被丢弃），比「不附着」更糟。因此 `cli::handle_cli_args()`
在**确认要打印之后**才调 `console::attach_for_cli()`——`Ok(None)`（没有 CLI 意图）直接返回，绝不碰控制台。

`main` 的顺序因此改成 CLI 在前：

```rust
fn main() {
    rollcaller_lib::cli::handle_cli_args();   // 命中即打印并 exit（不返回）
    rollcaller_lib::console::attach();        // GUI 启动：看开关
    tauri::async_runtime::block_on(rollcaller_lib::run());
}
```

两个附着入口共享同一份 `OnceLock` 状态，`attach_for_cli()` 用 `debug_assert!` 声明「必须早于 `attach()`」：
一个进程只走其中一条，通道状态只判定一次。

### 非 Windows

Unix 没有「附着」概念，变量被忽略（进程继承 0/1/2，终端启动天然可见，桌面启动写 `/dev/null`）。
变量名里的 `ON_WIN32` 就是明说这一点。
