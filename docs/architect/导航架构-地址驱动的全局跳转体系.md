# 导航架构：地址驱动的全局跳转

位置由地址表达（`#/<窗口名>/<段...>`），数据由载荷附带。任何窗口、任何来源的跳转走同一条链路：判定归属 → 本窗口落地，或交后端投递给目标窗口 → 目标窗口按地址铺路并交付载荷。

涉及路径均相对仓库根。

---

## 1 模型

### 1.1 地址

```
#/<host>/<seg1>/<seg2>/...
```

- `host` 为窗口名（`app` / `help`），小写，比较时大小写不敏感。两个层次各有一个类型：地址层是 `string`（`parseRoute` 须容忍 hash 中的任意段），域层是 Rust 导出的 `WindowKind`（`"app" | "help"` 闭集，`nav.install` 的 `host` 用它 ⇒ 写错即编译错误）。
- 其余段为不透明路径，语法归各域：help 为 `doc[/anchor]`，app 为入口链。
- 地址只表达位置，不携带数据。

### 1.2 Action 与幂等

一次跳转为 `Action { route, payload? }`。幂等判据是 route 与 payload 均相同；重放同一 Action 的语义是重新应用初始状态。

### 1.3 可深链判据

呈现只依赖可序列化输入，且所需状态能由这些输入与导航时可得的前置条件重建。

| 类型                 | 例                                                          | 可深链 |
|----------------------|-------------------------------------------------------------|--------|
| 只吃 id              | `edit-student` / `delete-student` / `edit-record`           | 是     |
| 零输入               | `create-student` / `import-student`                         | 是     |
| 页面视图的 id 快照   | `export-student` / `export-record`（`{filtered, selected}`） | 是     |

弹出位置不进载荷：触发元素标 `data-anchor={AppEntry.x}`，浮层以自身身份 `findAnchor(entry)` 查找，取不到则居中。

## 2 分层

### 2.1 前端：`frontend/src/lib/routing/`

每个窗口对应一个 `Domain`（状态与落地）与一个门面（动作）。通用层平铺在根上、只认 host；新增窗口即新增一个 `routing/<host>/`。

```
routing/
  address.ts            地址语法（纯值）
  domain.ts             域契约
  nav.ts                分发单例
  registry.ts           落点注册表
  app/
    domain.svelte.ts    app 域
    navigate.ts         app 门面
    entries.ts          ChildOf / chainOf / resolveAppChain
    transition.ts       转换语义
    entries.generated.ts
  help/
    domain.svelte.ts    help 域（含地址栈）
    navigate.ts         help 门面
    history.ts          地址栈纯函数
    payload.ts          载荷读取
    address.ts          HelpAddress
    entries.generated.ts
```

```
门面.enter / open → nav.go → parseAction
  → 判 host
     ├ 本窗口 → domain.decode → domain.land
     └ 他窗口 → forward → 后端投递 → 目标窗口 nav.go（冷启动为 nav.start(initial)）→ 同上
  → 落地成功才 replaceHash
```

| 文件                     | 职责                                                                         |
|--------------------------|------------------------------------------------------------------------------|
| `address.ts`             | `parseRoute` / `routeOf` / `canonicalRoute` / `parseAction` / `isRouteHref` / `hostOf`，只认语法 |
| `domain.ts`              | 域契约 `host` / `decode` / `encode` / `land`                                 |
| `nav.ts`                 | 唯一模块级可变状态：`install` / `go` / `start` / `currentRoute` / `replaceHash` |
| `registry.ts`            | 落点注册表，每窗口一张；只有叠加层注册                                       |
| `app/domain.svelte.ts`   | app 域：`decode = resolveAppChain`、`land = applyTransition`，`#shown` 为已落地链 |
| `app/navigate.ts`        | app 门面：`path` / `action` / `enter` / `leave`                              |
| `app/entries.ts`         | `ChildOf` / `chainOf` / `resolveAppChain`                                    |
| `app/transition.ts`      | `planTransition`（纯 diff）/ `applyTransition`                               |
| `help/domain.svelte.ts`  | help 域：`decode / encode` 走 `HelpAddress`，`land` 管加载、滚锚点、折叠树、栈、搜索预填 |
| `help/navigate.ts`       | help 门面：`open` / `back` / `forward` / `openSearch`                        |
| `help/history.ts`        | 地址栈纯函数 `pushAt` / `resetTo` / `stepIndex`，不依赖 rune                 |
| `help/payload.ts`        | `HelpPayload` 与 `readSearch`：从任意 JSON 载荷里取搜索词                     |
| `help/address.ts`        | `HelpAddress`：帮助地址的唯一解释者与拼装者                                  |
| `*.generated.ts`         | 生成物，勿手改，见 §4                                                        |

两个域的差异只收在各自的 `land`：app 是链 diff + 浮层注册表，help 是文档加载 + 滚动 + 栈。对 `nav` 而言两者是同一个接口。

门面只放动作，状态读域：`Help.svelte` 用 `helpNavigate.open / back / forward`，用 `helpDomain.current / canGoBack / pendingAnchor`；`App.svelte` 同形（`appNavigate.enter`、`appDomain.chain`）。域只在窗口根的 `nav.install` 与 `install(viewport)` 出现。

help 的搜索浮层是**唯一不进地址空间的浮层**：它是瞬态过程，关闭时不改变所在位置，而 app 的浮层是有地址含义的位置（`#/app/student-management/edit-student` 可深链、可重放）。强制给它地址就要在 `help` 的 `doc[/anchor]` 语法上再加一轴，且「打开搜索」与「停在某文档」将无法区分。打开它走 `helpNavigate.openSearch()`，不经 `Action`。

两份生成物的分工是单向的：主窗口不加载帮助锚点表；反向不设限 —— 帮助窗口要去 app 地址就直接调 `appNavigate`（如标题栏的 `enter("rollcall")`），代价只是与主窗口共享入口名表。

另有 `lib/types/overlays.ts`：按页 / 窗口分组的叠加层名字类型。`StudentOverlayName` / `RecordOverlayName` 由 `ChildOf` 派生；`HelpOverlayName` 与 `HelpOverlay` 句柄是帮助窗口的手写声明处。

### 2.2 后端：跨窗口投递

| 位置                                   | 内容                                                                                                                   |
|----------------------------------------|------------------------------------------------------------------------------------------------------------------------|
| `backend/src/state/nav.rs`             | `NavState`：按窗口名维护单槽待取载荷 —— `put`（覆盖式 last-wins）/ `take`（取走并清空）/ `clear`（窗口销毁时清理）   |
| `backend/src/cmd/nav.rs`               | `nav_open`（投递）/ `nav_take_pending`（取走）+ `NAV_WAKE_EVENT`（不带载荷）+ `host_of`（后端对 route 的唯一理解）     |
| `backend/src/windows.rs::open_by_host` | 按 `WindowKind` 分发建窗；返回值表示是否新建。窗口名 / label / html 入口全部来自该枚举，`NavState` 的键也是它          |

三条约束：

- **单槽而非队列**：投递语义是把窗口带到某个状态，不是消息。最新一次覆盖前一次。
- **存着等取，而非广播**：目标窗口可能懒创建，建窗时前端尚未监听，广播必丢。载荷先落后端、由前端主动取。
- **事件不带载荷**：载荷只走 pending 一条通路。没有单独的 ready 命令 —— 前端挂载后取一次，取走本身即就绪信号。

## 3 契约

### 3.1 Domain

| 成员      | 约束                                                                                                       |
|-----------|------------------------------------------------------------------------------------------------------------|
| `host`    | 本窗口名，等于地址第一段                                                                                    |
| `decode`  | 严格解释，失败返回 `null`；降级由 `nav` 统一处理                                                            |
| `encode`  | 与 `decode` 互逆（允许省略尾部默认段，只保证 `decode(encode(d))` 等价于 `d`）                                |
| `land`    | 目的地 → 视图；`payload` 为一次性命令参数，落地即消费，不从地址重建                                          |

- app 的 `decode` 是 `resolveAppChain`：要求段数等于链长且逐段与 `parentId` 一致。
- help 的 `decode` 不返回 `null`：非法锚点降级为文档顶部，空段降级为默认文档。放行 null 会让 webview 真的去导航（404）。

### 3.2 不变量

- **浮层可见 ⇔ 它是当前地址的链尾。** 打开一律走 `appNavigate.enter`，关闭一律走 `appNavigate.leave`（回退父级）。注册表的 `close` 只负责真正隐藏，由转换语义调用。
- `leave` 先比对当前地址是否就是该入口，不是则不动。没有这条，浮层 `clickOutside` 会在用户切卡片之后把地址拽回原处。
- **父链严格。** 生成期校验父存在、禁自指、禁成环；运行期 `resolveAppChain` 任一不符返回 `null` ⇒ 原地不动。完整路径是承重件（铺路即按链自顶向下 show），祖先段不是装饰。
- **卡片不注册 handler**，呈现为当前链的链首投影。若卡片也注册，链首与当前卡片会成为两份状态。

### 3.3 转换语义（app 的 `land`）

```
shared = 新旧链的共同前缀长度
旧的 shared 之后：逆序 close
新的 shared 之后：顺序 open（载荷只交给最深的一个）
整条链相同：diff 无动作，单独补一次目标的 open
```

| 场景                              | 结果                                  |
|-----------------------------------|---------------------------------------|
| `edit-student` → `delete-student` | 公共前缀含卡片 ⇒ 卡片不动             |
| 切到无关卡片                      | 前缀为空 ⇒ 全关再开                   |
| 重放同一地址                      | 补一次 `open`                         |

最后一格必要：关闭也回退地址，「地址停在目标、浮层已关闭」是常见状态，不补 `open` 则再次点击同一入口无反应。退回卡片时这次 `open` 落在无 handler 的卡片上，是预期的空操作。

### 3.4 载荷

载荷是目标本身（单个 id 为 `number`，一组 id 为 `number[]`，需预填时为对象），不带字段名。形状声明在 `app/meta.json` 的 `payload` 键，生成成 `AppEntryPayload` 后投影到三处：

| 端         | 位置                                       | 效果                            |
|------------|--------------------------------------------|---------------------------------|
| 构造侧     | `appNavigate.enter(entry, payload?)`       | 第二参由 `AppEntryPayload[E]` 反推 |
| 消费侧     | `registry.register(id, { open })`          | `open` 收同一份类型             |
| 地址侧     | `applyTransition → registry.open(id, raw)` | 载荷来自地址（跨窗口时为 JSON），落地前只能是 `unknown` |

`open` 实参为 `P | undefined`：地址可以没有载荷（深链只有地址），每个浮层开头判断一次。

浮层只快照 id，要显示的行按「仍存在」从 store 派生；编辑类另存草稿，草稿一旦存在就不再读 store，否则列表刷新会覆盖用户输入。

载荷白名单为 `string` / `number` / `boolean` 与 `[T]` / `{k: T}`，其余标识符当 `$types` 中的类型名。`bigint` 不在白名单：IPC 载荷走 `JSON.stringify`，真 bigint 会当场抛；`i64` 的 ts-rs 投影虽是 `bigint`，经 JSON 到达前端的实际是 `number`，待把该投影改为 `number`。

以上是 app 域。help 没有载荷声明表 —— `render_help` 不输出 payload，把它写进 `help/meta.json` 会**静默无效** —— 故类型手写在 `help/payload.ts`（`{search?: string}`），唯一消费者是搜索框预填。载荷从地址来时只能是 `unknown`，由 `readSearch` 宽进窄出。

### 3.5 降级

| 情形                           | 行为                                                   |
|--------------------------------|--------------------------------------------------------|
| 地址非法（切不出 host / 段）   | `nav.go` 返回 + warn                                   |
| 域解释不了（`decode` 返 null） | 原地不动 + warn，且不写 hash                           |
| 载荷非法或为空                 | 退化为纯导航（只切位置，不弹窗）                       |
| 锚点不存在                     | 滚到文档顶部                                           |
| nav 未安装                     | 忽略 + warn                                            |
| 入口名查询                     | 用 `Set` 而非 `in`，避免原型键命中                      |

## 4 声明 → 生成 → 类型约束

```
app/meta.json   （唯一手写处：id + parentId + payload，扁平节点树）
      │  scripts/codegen/routing_entries.py
      ├────────────────────────────────┐
      ▼                                ▼
routing/app/entries.generated.ts   routing/help/entries.generated.ts
      ├─ AppEntryPayload                └─ HelpRoute（句柄 → 完整地址）
      ├─ AppEntryId = keyof AppEntryPayload
      ├─ AppEntry            camelCase 句柄 → kebab 入口名
      └─ APP_ENTRY_PARENT    入口 → 父入口
```

帮助段在同一份文件里：`HelpRoute` 由 `help/meta.json` 的文档树与各文档 md 的 `{#anchor}` 派生；文档源既可能是 `resources/help/<id>/` 目录，也可能是仓库根同名文件（README / LICENSE / CHANGELOG / RELEASE_NOTES）。既无目录又无同名文件的节点不生成句柄。

名字出现在三处、全部受类型约束：联合类型成员、`register` 实参、`enter` 实参 ⇒ 应用代码里不出现入口名字面量。`ChildOf<P>` 由 `parentId` 推出某入口的直接子入口，页面写 `EntryRegistry<ChildOf<"student-management">>` ⇒ 在本页写记录页的浮层名会编译失败。

生成器自带两类校验：声明校验（父存在 / 不自指 / 不成环）与句柄唯一性（同域重名会静默覆盖）。

**生成时机**：`scripts/dev.py`、`build.py`、`test.py`、`bump.py` 调 `codegen.generate_all()`；tauri 的 `beforeDevCommand` 只启动前端 dev server，不生成。

**生成物守护**：`codegen.ensure_committed()` 在生成后比对 `git diff` 与 untracked，由 `scripts/test.py` 调用；quality-gate 跑 `test.py` ⇒ 生成物与声明不一致、或未提交，都会让流水线失败。

## 5 跨窗口时序

以「帮助窗口的按钮 → 删除主窗口里某批学生」为例：

```
① appNavigate.enter(deleteStudent, ids)        帮助窗口内发起
② nav.go → 规范化 → host 是 app ≠ help ⇒ forward
③ NavCommand.navOpen → 后端 nav_open
     WindowKind::from_host(route 第一段) → open_by_host（建窗或唤前台）→ put(pending) → emit_to 唤醒
④ app 窗口：NAV_WAKE_EVENT → nav_take_pending → nav.go
⑤ dispatch → appDomain.decode（严格校验父链）→ land → applyTransition → registry.open
⑥ 成功才 replaceHash，地址与界面同帧一致
⑦ 用户确认 → 删除 → appNavigate.leave(deleteStudent) → 地址回退到卡片
```

冷启动变体：目标窗口不存在 ⇒ 建窗且不发事件，载荷留在单槽；目标前端挂载后取一次。

## 6 已知缺口

| 项                             | 说明                                                                                                                                                                          |
|--------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 帮助 → app 的跨域入口未设计     | 正文里的 `#/<非 help host>/...` 链接在渲染期不被识别，点击交回浏览器原生，经帮助窗口的 `hashchange` 兜底再 `forward`；副作用是帮助窗口自身地址被改写。标题栏「主界面」按钮已走 `appNavigate.enter("rollcall")`，但正文链接仍无组件可用，也仍缺「跳到 app 任意入口」的表达 |
| help 的前进 / 后退不经 `dispatch` | `back` / `forward` 直接 `nav.replaceHash` + 加载。若要与「地址驱动」统一，需重新设计栈与地址的关系                                                                            |
| `restore` 入口未实现            | 弹窗按钮仅 `console.warn` 占位；`meta.json` 中未声明，故不触发注册完整性断言                                                                                                  |
| `HelpRoute` 有 6 个节点无句柄   | `rollcall` / `multi-rollcall` / `students` / `records` / `ui` / `about` 既无 `resources/help/<id>/` 也无仓库根同名文件                                                        |
| 测试只覆盖纯逻辑                | `frontend/tests/routing.test.mjs`（23 项）：地址原语、入口解析、注册表、`planTransition` / `applyTransition`、`appNavigate`、`nav.go` 归属判定、地址栈纯函数、载荷读取、生成物与声明一致。`*.svelte.ts`（`helpDomain` 的栈状态、`appDomain` 的 `$state`）与组件未覆盖 |

## 7 决策备查

| 决策点           | 选择                          | 理由                                      | 代价                                             |
|------------------|-------------------------------|-------------------------------------------|--------------------------------------------------|
| 位置与数据的划分 | 路径 = 位置，载荷 = 数据      | 地址可比较、可写 href、幂等判定简单       | 载荷必须可 JSON 序列化（`bigint` 要转 `number`） |
| 后端对地址的理解 | 只认第一段（host）            | 无需「域 → 窗口」映射表                   | 段语义完全归前端，后端无法校验路径合法性         |
| 跨窗口投递       | 单槽 pending + 无载荷唤醒事件 | 抹平懒建窗的监听时机；载荷只有一份真相    | 连续投递只保留最后一次                           |
| 卡片的呈现       | 不注册 handler，用链首投影    | 避免链首与当前卡片两份状态                | 注册完整性断言要排除根入口                       |
| 打开与关闭       | 都走地址                      | 地址成为全时真源，重放 / 深链 / 刷新自然一致 | 关闭会改变可观测地址                            |
| 名字来源         | `meta.json` 生成              | 改名即编译报错，且全仓可搜                | 必须跑生成器；生成物入库且禁止手改               |
| 帮助的栈         | 归 `helpNavigate`，只记用户点击 | 栈与是否入栈是同一事实的两面            | 一个类承担较多                                   |
| 测试设施         | 裸 node 跑纯逻辑              | 零依赖，且能 import 生产代码              | 测不到 `.svelte.ts` 与组件                       |
