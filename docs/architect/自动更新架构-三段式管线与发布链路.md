# 自动更新架构：三段式管线与发布链路

> 本文档以 **2856b1227140cebbe176dd442f007a8b2882e867**提交为主，描述 rollcaller 自动更新的完整形态：分层与状态机、对外契约、三阶段（检查 / 下载 / 安装）的实现细节、发布链路，以及每一项设计取舍的来历。
>
> 涉及路径均相对仓库根。

---

## 1. 概览

### 1.1 一句话

用户触发 → 后端 **检查**（拉版本索引挑目标版本 → 拉该版本清单）→ 后端 **下载**（.part 流式落盘 → sha256 + minisign 校验 → rename 为正式产物）→ 后端
**安装**（复验 → 分派 NSIS / Go updater → 清理并 `exit(0)`，安装器接管并重启）。

### 1.2 三层职责

| 层     | 位置                                                                          | 职责                                                      | 边界                    |
|--------|-------------------------------------------------------------------------------|-----------------------------------------------------------|-------------------------|
| 命令层 | `backend/src/cmd/update.rs`                                                   | 取共享 state、取当前版本、注入广播回调、把错误转 `String` | 不含业务判断            |
| 编排层 | `backend/src/service/update.rs`                                               | 阶段守卫、状态迁移、错误收敛、就绪锚点探测、安装前后编排  | 对外只返回 `UpdateView` |
| 领域层 | `backend/src/service/update/{version,check,verify,download,install,paths}.rs` | 版本判定、清单解析、拉取、校验、下载落盘、启动安装器      | 不感知状态机与 Tauri    |

支撑设施：`common/entity|enums|constant/update.rs`（类型与常量）、`state/update.rs`（会话 + 瞬时槽）、`state/http_client.rs`（命名 HTTP 客户端）。

### 1.3 五条贯穿全文的原则

| # | 原则                         | 体现                                                                                          |
|---|------------------------------|-----------------------------------------------------------------------------------------------|
| 1 | **后端状态机是唯一真源**     | 前端只镜像 `UpdateView`，不推断阶段、不自行维护状态                                           |
| 2 | **磁盘是产物的唯一事实源**   | 产物路径不入会话（由凭据现推）；"已下载"= 文件存在 + size 吻合 + 验签通过                     |
| 3 | **凭据不外泄、进度不入会话** | `Artifact` / 产物路径留在后端；进度落 `DownloadSlot` 原子槽，只走窄帧通道                     |
| 4 | **错误变体 = 重试命令**      | `UpdateError{Check/Download/Install}`，`type` 决定前端"重试"按钮调哪个命令                    |
| 5 | **签名不得静默降级**         | 主包产物签名必填（**fail closed**：空签名直接拒绝）；发布侧同样要求签名非空，否则拒绝产出清单 |

### 1.4 三种贯穿全文的维度

`AppMode` 由 `config/app_paths.rs` 推导：`cfg!(debug_assertions)` → `Develop`；exe 旁存在 `portable.mode` → `Portable`；否则 `Install`。

| 形态       | 判定                     | 用户数据根                 |   | 更新源  | 安装方式                                  |
|------------|--------------------------|----------------------------|:--|---------|-------------------------------------------|
| `Develop`  | `cfg!(debug_assertions)` | `<repo>/data`              |   | `Local` | Go updater 单文件覆盖 debug exe           |
| `Portable` | exe 旁有 `portable.mode` | `exe_dir/data`             |   | `CNB`   | Go updater 整目录替换（preserve `data/`） |
| `Install`  | 其余                     | `directories::ProjectDirs` |   | `CNB`   | NSIS 安装器                               |

更新源当前由形态 **硬定**，无用户可选，见 §11.3 。

## 3. 状态机与并发模型

### 3.1 状态与允许的迁移

`UpdateStatus`（内部）：`Idle` / `Checking` / `UpToDate` / `Available` / `Downloading` / `Downloaded` / `Error`。

| 当前阶段                                          | 可进入的命令           | 下一阶段                                                                                                             |
|---------------------------------------------------|------------------------|----------------------------------------------------------------------------------------------------------------------|
| `Idle`                                            | `check`                | `Checking` → `UpToDate` / `Available` / `Downloaded` / `Error`                                                       |
| `Checking`                                        | —（防重入）            | 同上                                                                                                                 |
| `UpToDate` / `Available` / `Downloaded` / `Error` | `check`                | 同上                                                                                                                 |
| `Available` / `Error(Download)`                   | `download`             | `Downloading`                                                                                                        |
| `Downloading`                                     | `cancel`（仅置取消位） | `Available`（取消）/ `Downloaded`（成功）/ `Error(Download)`（失败）                                                 |
| `Downloaded`                                      | `cancel` / `install`   | `Available`（取消并删产物）/ 进程 `exit(0)`（成功）/ `Error(Install)`（启动失败）/ `Error(Download)`（产物缺失损坏） |

### 3.2 防重入 = 阶段推导

不设置独立 `busy: bool`。`Checking` / `Downloading` 本身就是"忙"，命令入口的 `mutate` 闭包直接拒绝：

| 命令       | 拒绝条件                                                             | 文案                                              |
|------------|----------------------------------------------------------------------|---------------------------------------------------|
| `check`    | 阶段是 `Checking` / `Downloading`                                    | 更新操作正在进行中，请稍候再试                    |
| `download` | 阶段是 `Checking` / `Downloading`                                    | 检查更新正在进行中 / 下载已在进行中，请勿重复触发 |
| `download` | 阶段是 `Downloaded`                                                  | 幂等：直接返回当前视图                            |
| `download` | 其余（`Idle` / `UpToDate` / `Downloaded` 以外非 `Available`）        | 尚未检查到可用更新，请先执行 check                |
| `cancel`   | 无                                                                   | —                                                 |
| `install`  | `Checking` / `Downloading` / 既非 `Downloaded` 也非 `Error(Install)` | 更新尚未下载完成，请先执行 download               |

入口拒绝以 `Result::Err` 回到前端（`state` 未变更，前端直接提示）； **业务失败不报错**，而是折叠进 `UpdateView::Error`。

`mutate` 的语义：闭包返回 `Err` → 本次修改整体回滚（状态不落变更），因此"守卫 + 置位"可以安全地写在同一个闭包里。

### 3.3 并发结构

| 容器                                         | 内容                                                                            | 访问规则                                                                              |
|----------------------------------------------|---------------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| `UpdaterState.session: Mutex<UpdateSession>` | 阶段 + 展示信息 + severity + `artifact` 凭据 + `error`                          | 只经 `mutate`（短临界区，闭包内**禁止 `.await`**）/ `session()`（克隆快照）/ `view()` |
| `UpdaterState.slot: DownloadSlot`            | `downloaded: AtomicU64`、`total: AtomicU64`（`0` = 未知）、`cancel: AtomicBool` | 无锁；下载热路径（每 chunk）只碰原子                                                  |

下载过程中 **不碰 session
锁**：每 chunk `slot.set_progress()`，节流达阈值后 `slot.snapshot()` 回调窄帧。取消用 `&AtomicBool`（`Ordering::Relaxed`），下载循环每 chunk `load` 读到真实值——interior mutability 足够，无需 `Arc`（仅"未来多连接并发下载"才需要）。

### 3.4 错误收敛

```text
业务失败 → status = Error + error: Some(UpdateError{type, message})   （同锁写入）
视图投影 → UpdateView::Error(UpdateError)
前端     → 按 type 决定"重试"按钮调哪个命令，按 message 展示
```

| 失败位置                           | 变体       | 重试命令   | 备注                                                        |
|------------------------------------|------------|------------|-------------------------------------------------------------|
| 拉索引 / 拉清单 / 解析失败         | `Check`    | `check`    | 保留原会话内容（重试后覆盖），不触碰磁盘                    |
| 策略复核不通过（设置已变）         | `Check`    | `check`    | 文案"更新设置已变更，请重新执行 check"                      |
| 下载失败 / 取消之外的中断          | `Download` | `download` | 保留 `artifact` 凭据可重试                                  |
| 安装前发现产物缺失 / 校验失败      | `Download` | `download` | **磁盘事实被推翻 → 要求重下**，避免 `Error(Install)` 死循环 |
| 更新器准备失败（`ensure_updater`） | `Install`  | `install`  | 重试 install 会重跑 ensure                                  |
| 安装器启动失败                     | `Install`  | `install`  | 产物保留，进程存活可重试                                    |

用户取消 **不算错误**：`download` 域返回含 `CANCELLED` 的错误串 → 编排层识别后回 `Available`（可重下），`error` 清空。

## 4. 对外契约

### 4.1 命令

| 命令       | 入参 | 返回         | 副作用                                                                             |
|------------|------|--------------|------------------------------------------------------------------------------------|
| `check`    | —    | `UpdateView` | 网络（拉索引 + 可能拉清单）；写会话；广播终态                                      |
| `download` | —    | `UpdateView` | 网络；写会话；注入回调发迁移帧（view 通道）与进度窄帧（download 通道）             |
| `cancel`   | —    | `UpdateView` | 置取消位，或删已下载产物；广播终态                                                 |
| `install`  | —    | `UpdateView` | 读盘 + 复验 + 准备更新器 + 启动安装器；**成功路径进程退出**，失败返回 `Error` 视图 |
| `state`    | —    | `UpdateView` | 无网络、无副作用（挂载恢复现场用）                                                 |

命令名从简（`check` / `download` / `cancel` / `install` / `state`），本模块内无同名冲突。`download` / `install` 所需的当前版本由命令层从 `package_info().version` 取得后传入编排层—— **版本基线不入会话**。

### 4.2 `UpdateView`（裁剪契约）

`#[serde(tag = "status", content = "data", rename_all = "camelCase")]`

| 变体          | `status`      | `data`             | 前端渲染                                |
|---------------|---------------|--------------------|-----------------------------------------|
| `Idle`        | `idle`        | —                  | "检查更新"按钮                          |
| `Checking`    | `checking`    | —                  | 转圈                                    |
| `UpToDate`    | `upToDate`    | —                  | "已是最新版本"                          |
| `Available`   | `available`   | `{info, severity}` | 版本 / 日期 / Changelog / severity 徽标 |
| `Downloading` | `downloading` | `{info}`           | **纯状态**，进度数字来自 download 通道  |
| `Downloaded`  | `downloaded`  | `{info, severity}` | "重启并更新"                            |
| `Error`       | `error`       | `{type, message}`  | 文案 + 按 `type` 重试                   |

`UpdateInfo` = `{version, notes, date}`（`notes` 直接渲染为 Markdown）。`Artifact`（`url` / `sha256` / `signature` / `size`）、产物路径、`Policy`、`HistoryVersion` **一律不出现在视图里**，也不导出 TS。

导出给前端的类型（`#[ts(export)]`）：`UpdateView`、`UpdateInfo`、`UpdateError`、`DownloadProgress`、`Severity`（以及 `AppMode` 等配置类）。

### 4.3 双通道事件

| 通道          | 事件名                         | 载荷                                  | 语义                                                          |
|---------------|--------------------------------|---------------------------------------|---------------------------------------------------------------|
| view 通道     | `rollcaller://update/view`     | `UpdateView`                          | **状态迁移帧**（含进入 `Downloading` 这一次）+ 各命令**终态** |
| download 通道 | `rollcaller://update/download` | `DownloadProgress{downloaded, total}` | 仅 `Downloading` 期的**进度窄帧**（节流）                     |

设计要点：

- **同通道内 emit 有序**，所以迁移帧不可能迟到于终态；
- 进度与状态拆通道 = **隔离陈旧帧**：进度帧无论何时到达都无法把 UI 从终态打回"下载中"；
- `download` 命令在编排层注入两个回调：`on_view`（确认进入下载时广播一次迁移帧）、`on_progress`（节流 100 ms 后从原子槽读快照广播）；
- 命令返回值与广播共用同一类型、同一 apply 逻辑；广播失败静默（前端随后可经命令返回值校准）。

### 4.4 前端镜像

`frontend/src/lib/stores/UpdateStore.svelte.ts` 是唯一 store，`Updater.svelte` 是唯一消费组件。

| 机制         | 实现                                                                                    |
|--------------|-----------------------------------------------------------------------------------------|
| 双通道订阅   | `#view`（view 通道）与 `#progress`（download 通道）两个独立槽                           |
| 陈旧帧防护   | download 通道回调**仅当 `#view.status === "downloading"` 才接受**                       |
| 进度瞬时性   | `#apply` 在**进入或离开** `downloading` 时重置 `#progress`                              |
| 幂等订阅     | `subscribe()` 只注册一次，两个 `unlisten` 组合释放                                      |
| 挂载初始化   | `init()` = 订阅广播 + `state()` 拉一次快照（无网络）                                    |
| 自动检查     | `onMount`：**仅当拉到的快照是 `idle`** 才自动 `check`（其余阶段不自动推进，防错误推进） |
| 入口拒绝提示 | `#run` 捕获 `Err` 记入 `lastError`，不影响 `#view`                                      |

多窗口现状：只有主窗口渲染本组件、也只有主窗口 autoCheck。后端广播本就喂全窗口，设置窗口后续接入时需重审多实例订阅与 autoCheck 归属（代码内有 TODO）。

## 5. 检查（check）

### 5.1 流程

```
1. GET versions.json                                   ← 每次检查都拉取（不缓存）
2. pick_target：筛 version > current → 按版本倒序 → 首个被 evaluate 放行者为目标
   无放行者 → Ok(None)（无更新）
3. GET 该版本清单 latest-{github|cnb|develop}.json
   └─ 缓存优先：cache/update/{source}/{version}.json（命中即免网络；损坏则删后回源并重写）
4. validate_manifest：索引 ↔ 清单一致性复判 → 按 (OS, ARCH, mode) 取产物
   └─ 无对应产物 → Ok(None)（无更新，不打扰用户）
```

`versions.json` 每次发布都会新增条目，缓存无意义； **目标版本清单按"源 + 版本"寻址后可以长期复用**，同一目标版本再次被选中时直接读盘。清单缓存写失败只 `warn`（不阻断检查）。

### 5.2 两段式拉取的理由

版本索引携带 **全部历史版本的 severity**，因此 `(current, latest]` 区间内"最高可安装版本" **可能不是** latest：

| 场景                                 | latest              | 中间版本                   | 结果             |
|--------------------------------------|---------------------|----------------------------|------------------|
| latest 是普通补丁、被 Minor 门槛挡下 | 0.4.6 `normal` 被挡 | 0.4.5 `important` 豁免达标 | 目标 = **0.4.5** |
| latest 直接达标                      | 0.4.6               | —                          | 目标 = 0.4.6     |
| 区间内全被挡                         | —                   | —                          | 无更新           |

### 5.3 决策分层

判定语义只写一次，`check` 与 `download` 入口复核共用同一个纯函数 `check::evaluate`。

| 层     | 位置                                                 | 语义                                                             |
|--------|------------------------------------------------------|------------------------------------------------------------------|
| 纯策略 | `version::decide(current, latest, level, channel)`   | 只管"通道门禁 + 幅度门槛"，不认识 `severity`，保持纯 `Copy` 枚举 |
| 融合层 | `check::evaluate(current, latest, policy, severity)` | 叠加 severity 豁免与 critical 穿透                               |

`decide` 的六步（顺序即优先级）：

1. `level == Never` → `Skip`
2. 稳定通道下 latest 是预发布 → `Skip`（保证 Stable 用户接触不到任何预发布）
3. `latest <= current` → `Skip`（ **不允许降级**）
4. `current` 预发布、`latest` 稳定（ **逃逸通道**）→ `Update`
5. 两者皆预发布（ **通道内递进**）→ `Update`
6. 其余 → 按数字变化幅度对门槛（floor）判断

**floor 而非 cap**：门槛表示"最小可接受更新单元"。桌面软件没有 API 兼容包袱，用户嫌的是"更新太频繁"而非"变化太大"；被跳过的补丁不是丢失，而是 **延迟聚合**——等下一个达标版本一次跳过去。

| floor \ 变化 | 补丁 1.2.1→1.2.2 | 次版本 1.2.1→1.3.0 | 主版本 1.2.1→2.0.0 |
|--------------|------------------|--------------------|--------------------|
| `Patch`      | 更新             | 更新               | 更新               |
| `Minor`      | 跳过             | 更新               | 更新               |
| `Major`      | 跳过             | 跳过               | 更新               |
| `Never`      | 跳过             | 跳过               | 跳过               |

预发布的三条特殊路径（风险不同，故规则不同）：

| 场景                        | 性质                   | 规则                                         |
|-----------------------------|------------------------|----------------------------------------------|
| `1.2.0` → `1.3.0-rc.1`      | 通道切换（stable→pre） | 需通道 = `Prerelease`，且**仍按门槛**        |
| `1.2.0-rc.1` → `1.2.0-rc.2` | 通道内递进（pre→pre）  | 跟随通道，**绕过门槛**（进通道时风险已接受） |
| `1.2.0-rc.1` → `1.2.0`      | 逃逸通道（pre→stable） | **无条件更新**（否则用户永远卡在预发布）     |

### 5.4 severity 豁免矩阵

| `decide` 返回 Skip 的原因       | `normal` | `important`     | `critical`                  |
|---------------------------------|----------|-----------------|-----------------------------|
| 幅度不足                        | 不通知   | **豁免 → 通知** | 豁免 → 通知                 |
| 用户关闭更新（`level = Never`） | 不通知   | 不通知          | **穿透 → 通知（强制更新）** |
| 稳定通道拦预发布                | 不豁免   | 不豁免          | 不豁免                      |
| 同版本 / 降级                   | 不豁免   | 不豁免          | 不豁免                      |

实现方式：豁免 = **仅把幅度门槛临时降到 `Patch`**，其余门禁原样交给 `decide`。这样无需给 `decide` 增加"Skip 原因"、也不破坏其纯 `Copy` 形态。强制更新 = `critical`，即使 `level = Never` 也穿透放行。

### 5.5 一致性复判

索引只做预筛选， **清单才是该版本的最终发布数据**：

| 检查                                    | 不一致时                                  |
|-----------------------------------------|-------------------------------------------|
| `manifest.version != 索引指向的版本`    | `Err`（发布端错误，宁可暴露也不静默降级） |
| 用清单**自身**的 severity 复判 → `Skip` | `Err`                                     |
| 当前 `(OS, ARCH, mode)` 无对应产物      | `Ok(None)`（视为无更新）                  |

### 5.6 起始版本

`LATEST_MANIFEST_START_{GITHUB,CNB}` 与 `VERSIONS_INDEX_START_{GITHUB,CNB}` 均为 `0.8.0`：索引 / 清单 / 签名自该版本起才存在于远端，更早的历史版本在 GitHub / CNB 上无对应文件。由于索引候选恒不低于起始版本，流程无需对起始版本做特判。

## 6. 下载（download）

### 6.1 落盘三段式

```
temp/downloads/{随机uuid32}.part   ──校验通过──▶  temp/update/packages/{url 最后一段}
        （无信息量的名字、非可执行扩展名）              （正式产物名，自带版本/平台/架构）
```

| 步骤 | 内容                                                                      |
|------|---------------------------------------------------------------------------|
| 0    | 确保 `part` 父目录与 `final` 父目录存在（两者分居两目录，均可能尚未创建） |
| 1    | `final` 已存在 → 先整体验签：通过即幂等返回；失败则删除待重下             |
| 2    | GET 下载源；`!is_success` → `Err`（"服务器返回 HTTP {status}"）           |
| 3    | 逐 chunk 写 `.part`：每 chunk 检查取消位、写盘、上报进度                  |
| 4    | 校验 `.part`（`verify_artifact_path`）；失败删除 `.part` 并附上下文       |
| 5    | `rename` 为正式名（同卷跨目录原子；同名残留已在步骤 1 处理）              |

**磁盘上从不出现"未验证的正式产物"**：正式落点一定是已验证字节。

### 6.2 就绪锚点

`ready_artifact(path, artifact)`（编排层）：文件不存在 → `None`； **先以 `size` 短路**（不符即视为损坏、删除）；再整体验签（失败即删除）。命中返回 `Some(路径)`。

使用点：`check` 命中时探测（命中即把状态投影为 `Downloaded`——恢复现场，可跳过下载直接安装）；`download` 入口探测（命中即跳过下载，但 **不跳过验签**）。损坏一律清除待重下。

### 6.3 校验

| 项          | 规则                                                                                                                                 |
|-------------|--------------------------------------------------------------------------------------------------------------------------------------|
| sha256      | **必验**，十六进制小写比对（`to_ascii_lowercase`）                                                                                   |
| minisign    | `signature` **必填**：空即拒绝（fail closed）；只验完整性的场景用独立原语 `verify_sha256`                                            |
| 双重 base64 | 清单 `signature` 与公钥内容都是 **base64(minisign 文本)**：先 STANDARD base64 解外层，再交 `minisign-verify` 解内层                  |
| 内存语义    | `minisign-verify` 只支持整段字节（`&[u8]`），故路径形态也必须整读；sha256 复用同一份字节，不再自维护流式哈希（两种方式峰值内存相同） |
| 公钥来源    | `common/constant/secrets.rs::ROLLCALLER_UPDATE_PUBKEY`（内联 base64 常量，与 `rollcaller.pub.key` 等值）                             |

互操作（`tauri-cli ≥ 2.11`）：

| 步骤       | 命令                                                 | 产物                            |
|------------|------------------------------------------------------|---------------------------------|
| 生成密钥对 | `tauri signer generate --ci -p <密码> -w <名称>.key` | `<名称>.key` + `<名称>.key.pub` |
| 填公钥     | 把 `.pub` 全文填入 `ROLLCALLER_UPDATE_PUBKEY`        | —                               |
| 对产物签名 | `tauri signer sign <文件> -f <名称>.key -p <密码>`   | `<文件>.sig`                    |
| 填签名     | 把 `.sig` 全文填入清单 `signature`                   | —                               |

≥ 2.11 的 `.pub` / `.sig` **本身就是 base64 (minisign 文本)**，可直接取用，
**不得再编码一次**；更早版本才产出明文 minisign 文本。`verify.rs` 内有 `interop_with_tauri_signer` 测试做真实互操作验证（本机无 tauri CLI 时自动跳过）。

### 6.4 传输与超时

| 客户端 | 获取方式                  | 配置                                                         |
|--------|---------------------------|--------------------------------------------------------------|
| 常规   | `http_client::client()`   | 总超时 30 s、连接 10 s、池 10/host、90 s 空闲回收、浏览器 UA |
| 下载   | `http_client::download()` | **无总超时**（防大包被截断）、连接 10 s、**空闲读超时 60 s** |

两个客户端都是 `&'static`（注册表持有，连接池复用）。`timeout` 为 `None` 时 reqwest 不设整体超时，靠 `read_timeout` 兜底"对方卡死"。

### 6.5 断点续传现状（未实现，但有实测依据）

| 源     | 能力               | 依据                                                                                                                                                                              |
|--------|--------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| GitHub | **支持**（未实现） | 原始下载链接返回 302 → `release-assets.githubusercontent.com`（Azure CDN），响应头含 `Accept-Ranges: bytes`；重试时重新请求原始链接（自动跟随重定向拿新令牌）+ `Range` 头即可续传 |
| CNB    | **不支持**         | 实测携带 `Range: bytes=0-99` 仍返回 `200 OK` + 全量 `Content-Length`，而非 `206 Partial Content`                                                                                  |

当前策略：失败 / 取消即全量重下。未来若在 GitHub 上实现多线程 / 续传，注意 `paths::part()` 的随机名需改为按下载任务稳定命名，且本地联调源也得补 206（见 §8.4）。

### 6.6 进度与取消

| 机制         | 实现                                                                                  |
|--------------|---------------------------------------------------------------------------------------|
| 进度写       | 每 chunk `slot.set_progress(DownloadProgress{downloaded, total})`（只 store 原子）    |
| 进度读       | 节流 `PROGRESS_BROADCAST_INTERVAL = 100 ms` 后 `slot.snapshot()` → `on_progress` 窄帧 |
| `total` 语义 | 来自 `Content-Length`；原子槽用 `0` 哨兵表达"未知"，`snapshot` 还原为 `None`          |
| 取消置位     | `cancel` 命令 → `state.request_cancel()`（仅置位）                                    |
| 取消感知     | 下载循环每 chunk `load(Relaxed)`；置位 → 删 `.part` → `Err("CANCELLED")`              |
| 复位         | 编排层在下载结束（成功 / 失败 / 取消**全部**）复位取消位与进度槽                      |
| 已完成再取消 | 删正式产物 → 回 `Available`（保留 `info` 与凭据，可重下）                             |

## 7. 安装（install）

### 7.1 编排（`service/update.rs::install`）

```
守卫（仅 Downloaded / Error(Install) 可进入）
  → 取 artifact 凭据 + 目标版本
  → 产物路径现推 paths::package(artifact.file_name()?)
  → 读盘 → verify_artifact 二次整体验签
      ├─ 读失败 / 校验失败 → Error(Download)（要求重下）
  → install::ensure_updater(mode).await      （Portable / Develop：幂等准备更新器）
      └─ 失败 → Error(Install)（可重试 install）
  → install::launch(mode, path, from, to)
      └─ 失败 → Error(Install)（产物保留、进程存活、可重试）
  → install::finish_and_exit().await         （永不返回：shutdown_hooks → exit(0)）
```

安装阶段 **再次整体验签**是刻意的：`Downloaded` 状态不代表产物仍然有效（用户可能手工删改、磁盘可能损坏）——磁盘是事实源，所以这里兜底校验。

`finish_and_exit()` 只应在"确认即将退出"时调用（即 `launch` 成功之后）：失败路径进程继续存活，被清理过的资源（如已关闭的数据库）不应被仍在运行的进程使用。

### 7.2 NSIS（`Install` 形态）

| 项       | 内容                                                                                                                                                                                   |
|----------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 启动     | `ShellExecuteW`（`windows_sys`），返回值 `<= 32` 视为失败                                                                                                                              |
| 界面模式 | `BasicUi` 无参数 / `Silent` → `/S` / `Passive`（默认）→ `/P`                                                                                                                           |
| 重启     | `BasicUi` 不自动重启；其余 → `/R`                                                                                                                                                      |
| 参数拼装 | `[界面参数] /UPDATE [/R /ARGS <逐项转义的原启动参数>] [用户自定义参数]`                                                                                                                |
| 转义     | `escape_nsis_current_exe_arg` 与 `encode_wide` **原样搬运自 `tauri-plugin-updater` v2**（含全部测试），规则不得自创或简化——它额外转义了 `/`，避免 NSIS 把 `/` 开头的内容当成自己的参数 |
| 集成方式 | 安装包需用 NSIS 构建并识别 `/UPDATE`、`/R`、`/ARGS`（由 tauri bundler 生成的 nsis 脚本天然支持）                                                                                       |

重启由安装器完成，本进程在此之前 `exit(0)`；原启动参数经 `/ARGS` 传递，使重启后的应用继承同样的命令行。

### 7.3 Portable（`Portable` 形态）

```
find_updater()（cache/update/bin 内发现，由 ensure_updater 先备好）
  → 当前 exe 路径 → target_dir = exe 所在目录，data_dir = target_dir/data
  → extract_zip(portable.zip) → temp/update/staging/portable-source-{目标版本}/
  → 组装 config → temp/update/config/portable-config-{from}-to-{to}.json
  → 分离式 spawn updater.exe <config>
  → （编排层收尾）exit(0)  → updater: wait → update → launch →（失败则 rollback）
```

config 关键语义（与 Go updater `config.schema.json` 对齐，字段写全、路径统一正斜杠）：

| 字段                         | 值                                              | 理由                                                                                       |
|------------------------------|-------------------------------------------------|--------------------------------------------------------------------------------------------|
| `wait.pid`                   | 本进程 PID                                      | updater 等本进程 `exit(0)` 后才动文件；`timeout 10000` / `forceKill true` / `interval 500` |
| `update.source`              | 解压后的目录                                    | **Go updater 不会自动解压 zip**，source 必须是已解压目录                                   |
| `update.target`              | exe 所在目录                                    | 程序目录                                                                                   |
| `update.preserve`            | `[data_dir]`                                    | 替换 target 时保留用户数据                                                                 |
| `update.cleanBeforeCopy`     | `true`                                          | Portable 是整目录替换语义                                                                  |
| `update.backup.enabled`      | `true`                                          | 允许失败回滚；`location` 留空 = updater 自动生成（target 兄弟目录 + 时间戳）               |
| `update.backup.exclude`      | `[data_dir]`                                    | 备份不含用户数据（巨大且无需还原）                                                         |
| `launch.execution`           | `direct` + 当前 exe 路径                        | 重启自身                                                                                   |
| `launch.context.workspace`   | target_dir                                      | 工作目录                                                                                   |
| `launch.lifecycle.stayAlive` | `0`                                             | 启动新进程后**分离并退出**（不驻留）                                                       |
| `rollback.enabled`           | `true` + `fallbackExecutable` + `maxAttempts 2` | launch 失败则还原本目录并拉起旧 exe                                                        |

config 与解压内容 **刻意分居**（`temp/update/config` vs `temp/update/staging`）：否则会被 updater 当作 source 一起复制进 target。

### 7.4 Develop（`Develop` 形态）

与 Portable 共用同一套 runner，只差 config 语义——因为 **target 是编译目录**（`backend/target/debug`）：

| 字段                         | 值                                              | 理由                                                                                                 |
|------------------------------|-------------------------------------------------|------------------------------------------------------------------------------------------------------|
| `update.cleanBeforeCopy`     | **`false`**                                     | **绝不能整目录清理**：其余中间产物（`*.o` / `*.d` / `*.rlib` / PDB）必须保留，updater 只覆盖同名文件 |
| `update.preserve`            | `[]`                                            | target 内无用户数据                                                                                  |
| `update.backup.enabled`      | `false`                                         | 整目录备份无意义且巨大                                                                               |
| `rollback.enabled`           | `false`                                         | 产物已整体验签，覆盖前失败可重试                                                                     |
| `launch.execution.path`      | `target_dir/rollcaller-update-from-develop.exe` | **不是当前 exe**（见 §10.9）                                                                         |
| `launch.context.workspace`   | target_dir 的上两级（cargo workspace 根）       | 祖先不足两级视为布局错误，**允许 panic 但 panic 文案带出实际 `target_dir`**                          |
| `launch.lifecycle.stayAlive` | `0`                                             | 分离启动，让新实例活下来（见 §10.10）                                                                |

载荷形态：`develop` 槽（与 `nsis` / `portable` 同级）的 zip 内是 debug exe，文件名固定为 `DEVELOP_UPDATE_BIN_NAME = rollcaller-update-from-develop.exe`， **后端常量与 `scripts/common/packager.py`
的常量必须逐字符一致**。

Develop 无 `develop` 槽 = 该版本无产物 = 无需更新（不回退 nsis）。

### 7.5 Go updater 契约（外部仓库 `github.com/bytecascade-Lee/updater`）

本仓库只依赖它的 **命令行契约**，不依赖其内部实现。

| 项           | 内容                                                                                                                              |
|--------------|-----------------------------------------------------------------------------------------------------------------------------------|
| 调用方式     | `updater.exe <config.json 路径>`（唯一位置参数）                                                                                  |
| 流程         | `wait → update → launch →（可选）rollback`                                                                                        |
| 退出码       | `0` 成功 / `2` wait 失败 / `3` update 失败 / `4` launch 失败（含回滚成功）/ `5` 回滚失败                                          |
| 回滚触发条件 | `launch` 失败**且** `rollback.enabled` **且** `update.backup.enabled`                                                             |
| 回滚行为     | 备份整目录复制回 target；`fallbackExecutable` 非空则以分离方式拉起旧 exe（重试 `maxAttempts` 次，默认 1）；为空则仅还原不启动进程 |
| 路径要求     | `launch.execution.path`、`update.*`、`workspace`、`logFile` 均须**绝对路径**                                                      |
| 分离语义     | `stayAlive == 0` → 新进程以 `DETACHED_PROCESS \| CREATE_NO_WINDOW` 启动，**不继承控制台**，且此分支**不读 `captureOutput`**       |
| 更新器自身   | 只有 sha256，无 minisign 签名                                                                                                     |

分离式 spawn（本进程侧，`install/common.rs`）：

```rust
CREATE_NEW_PROCESS_GROUP | DETACHED_PROCESS
```

使 updater 不随本进程退出而终止，独立完成更新流程。

### 7.6 更新器就绪（`ensure_updater`）

挂接在编排层 `install` 的 **异步段**，仅 `Portable` / `Develop` 需要（`Install` 直接返回）：

```
1. find_updater() 已在 cache/update/bin 发现更新器 → 幂等返回（不重复下载）
2. GET 更新器仓库 latest manifest（与主源一致用 CNB）
3. 按当前 (OS, ARCH) 索引扁平清单：value["windows"][arch].{url, sha256, size}
4. 下载（体积小，内存收齐）→ size 比对 → verify_sha256 → 写 cache/update/bin/{url 最后一段}
```

两处刻意选择：

- **不建结构体**：更新器清单是扁平结构（无 `platforms` 包装、无 `nsis`/`portable` 载荷层、无 `signature`、无 `severity`），直接 `serde_json::Value` 索引即可；为该结构建 struct 属过度设计。
- **不走标准 Artifact 管线**：落点是 **持久 cache**（而非会被清理的 temp），且仅 sha256；代码内注明"**一旦更新器支持 minisign，本函数即废弃**"，届时走标准 `verify_artifact_path`（现已 **签名必填、fail
  closed**，届时需为更新器产物真出签名；届时需为更新器产物补出签名）。

`find_updater()` 的行为：扫描目录内全部 `.exe` → 逐个执行 `-v` 并用正则提取 semver → 取版本最大者 → 删除其余（含解析失败的）→ 按 `<name>-<semver>-<platform>-<arch>.exe` 重命名保留文件 → 无有效版本则全删返回 `None`。因此
**更新器产物名必须遵守该命名约定**，且调用方须知晓"发现"动作会执行并清理目录内其它 exe。

## 8. 端到端接力（以 Portable 为例）

| #  | 执行者     | 动作                                                               | 进程状态 |
|----|------------|--------------------------------------------------------------------|----------|
| 1  | 应用程序   | `check` → 命中 → `Available{info, severity}`                       | 运行     |
| 2  | 应用程序   | `download` → 迁移帧广播 → 流式下载 → 校验 → rename                 | 运行     |
| 3  | 应用程序   | 状态 → `Downloaded`，终态广播                                      | 运行     |
| 4  | 应用程序   | `install` → 读盘复验 → `ensure_updater` → 解压 → 写 config         | 运行     |
| 5  | 应用程序   | 分离式 spawn `updater.exe <config>`                                | 运行     |
| 6  | 应用程序   | `shutdown_hooks::run_all()`（如关数据库）→ `std::process::exit(0)` | **退出** |
| 7  | Go updater | `wait`：等 pid 退出（或超时强杀）                                  | 运行     |
| 8  | Go updater | `update`：备份 target（排除 data）→ 清空 → 从 staging 复制         | 运行     |
| 9  | Go updater | `launch`：以分离方式启动新 exe                                     | 运行     |
| 10 | Go updater | 进程退出（stayAlive = 0）                                          | **退出** |
| 11 | 新应用实例 | 接管（读同一份 `data/`）；staging 由后续清理规则兜底               | 运行     |

失败分支：第 8 步失败 → 退出码 3（备份已在，可人工恢复）；第 9 步失败且回滚启用 → 还原备份 + 拉起旧 exe → 退出码 4；回滚也失败 → 退出码 5。

`Install` 形态的第 7–11 步换成 NSIS：安装器接管、自动重启（`/R`），同样带原启动参数。

### 8.4 本地联调（`Develop` 源）

`scripts/local_update_source_server.py` 模拟远端发布源：

| 项                    | 内容                                                                                                                                                               |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 监听                  | `localhost:14652`（host / port 为常量，与后端 `constant/update.rs` 的 `DEVELOP` 系列逐字符一致）                                                                   |
| 路由                  | `/rollcaller/releases/latest/download/{versions.json,latest-develop.json}`、`/rollcaller/releases/download/v{版本}/{latest-develop.json,产物}`                     |
| 只 serve 一个版本目录 | `release/Local/<版本>+<构建信息>/`；同版本多目录取提交数最多者；缺 `latest-develop.json` / `versions.json` 或没有任何 `.exe`/`.zip` 即报错退出（**不做自动生成**） |
| 版本校验              | 路径中的版本（可带前导 `v`）须与 serve 版本一致，否则 404                                                                                                          |
| 防穿越                | 解析后必须仍在 serve 目录内且为文件                                                                                                                                |
| `--rate`              | **仅产物直链**限速，单位 KB/s（**1024 进制**），默认 `4096`，`0` = 不限速；清单 / 索引不受限速                                                                     |
| 限速实现              | `StreamingResponse` + **同步**生成器 `for + sleep`；分块自适应 `chunk = max(1, min(64KiB, rate//2))` 使每 tick ≤ 0.5 s                                             |
| 配速                  | 按 deadline（起始时刻 + 已发字节 / 速率）而非逐块 sleep，消除累计漂移                                                                                              |
| 必须自补的响应头      | `Content-Length`（否则退化为 chunked → reqwest `content_length()` 为 `None` → 进度条总长丢失）、`Content-Disposition`、`Accept-Ranges: none`                       |
| 已知缺口              | 限速路径不支持 Range / 206（与 CNB 现状一致）；将来 GitHub 源实现续传 / 多线程时需补单 / 多区间 206 并让限速作用于每个分段                                         |

两条易踩的坑：

- 同步生成器 **必须保持同步**——starlette 用 `iterate_in_threadpool` 跑同步迭代器，`time.sleep` 在线程池里不阻塞事件循环；写成 `async def` + `time.sleep` 会拖死清单请求。
- FastAPI 的 `APIRoute` 只注册 GET（不像 starlette `Route` 自动附带 HEAD），故本服务所有路由 `HEAD → 405`（历来如此）。

## 9. 目录布局

`paths.rs` 是布局的唯一出口，调用方只传可变信息（文件名 / 版本 / 源 / 形态）。

| 路径                                                   | 语义                        | 生命周期                               |
|--------------------------------------------------------|-----------------------------|----------------------------------------|
| `cache/update/{source}/{version}.json`                 | 目标版本清单缓存            | 持久复用（按源 + 版本寻址）            |
| `cache/update/bin/{file_name}`                         | Go updater 可执行文件       | 工具属性，缓存复用（按文件名区分版本） |
| `temp/update/packages/{file_name}`                     | 已下载待安装的主包产物      | 临时：安装即弃，允许他版本残留         |
| `temp/update/config/{mode}-config-{from}-to-{to}.json` | 一次安装会话的 updater 配置 | 临时：安装过程专属                     |
| `temp/update/staging/{mode}-source-{version}/`         | 压缩包解压暂存              | 临时：安装过程专属                     |
| `temp/downloads/{uuid32}.part`                         | 下载中的工作区              | 随时可删                               |
| `logs/u/{mode}-update-{from}-to-{to}-{micros}.log`     | Go updater 运行日志         | 排障用                                 |

**布局原则**：

1. **产物平铺、文件名自带完整信息**——文件名取发布产物 url 最后一段（如 `rollcaller-0.1.2-windows-x86_64-setup.exe`），即"一次下载目标的唯一标识"；就绪探测、复验、取消清理全部按文件名寻址，无需额外版本目录。
2. **目录按内容的生命周期与语义分派**——持久复用（cache）/ 临时即弃（temp/packages）/ 工作区（temp/downloads）/ 安装过程专属（temp/config、temp/staging）。
3. **part 与正式产物刻意分居**——part 是不完整、随时因校验失败或取消而删除的工作区；未来断点续传 / 多进程下载的临时文件也共居此处；两者同在 app 自管 temp 卷内，跨目录 `rename` 原子。

`bootstrap` 只预建六个
**顶层**目录（config / data / cache / temp / logs / webview2），故 `temp/update/config` 等深层目录由各写入点自行 `create_dir_all`（`fs::write` 不创建父目录）。这一点在首次真跑 Portable / Develop 安装时暴露过（os error 3）。

**temp 清理规则：目前未实现**。设计意图是"app 自管 temp 不被系统清理，但也不能无限增长"，约定为按启动日期判断（日期被 3 整除时清理），届时就绪产物随之丢失 → 触发重下（符合 temp 语义）。见 §11.3 的讨论。

## 10. 设计动因与踩坑史

本章回答"**为什么长这样**"。每条都是实际发生过的现象或明确的取舍，不是事后合理化。

### 10.1 为什么自己设计更新管线，弃用 `tauri-plugin-updater`

| 项   |   | 内容                                                                                                                                                                                                                                                                |
|------|:--|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 起点 |   | 前端用官方插件：只支持 NSIS 安装包；清单格式固定；无法在没有动态更新服务器的情况下承载"便携版整目录替换""开发模式直更""severity / 强制更新"                                                                                                                         |
| 目标 |   | 后端设计统一管线：`check → download → minisign 验签 → 安装分派（NSIS / Portable / Develop）`，自定义 `latest-*.json` 清单，仅 Windows x86_64 / arm64                                                                                                                |
| 终局 |   | 插件被彻底移除：`Cargo.toml` 依赖、`lib.rs` 注册、`tauri.conf.json5` 的整个 `plugins.updater` 块、`capabilities/desktop.json`（唯一权限就是 `updater:default`，整文件删除）、前端 `pnpm remove @tauri-apps/plugin-updater`                                          |
| 隐藏 |   | 移除后暴露 9 个 `E0277: semver::Version: Deserialize not satisfied`——项目自己的 `semver = "1.0.28"` **没开 `serde` feature**，一直靠插件传递启用而"白拿"。修复：显式声明 `features = ["serde"]`。**教训：显式声明自己真正用到的 feature，别吃依赖的传递 feature。** |
| 清理 |   | `tauri-plugin-process` 成为孤儿（原本只服务前端 `relaunch()`；现在重启交 NSIS `/R` 与 updater launch、退出走 `std::process::exit(0)`），一并移除（依赖 + 注册 + `process:default` 权限 + 前端包）                                                                   |

### 10.2 为什么前端只拿"极简 view"

前端真正需要的只有： **到了哪个阶段**、 **目标版本 / 说明 / 日期**、 **severity**、 **错误文案 + 该重试哪个命令**。

因此：

| 决策             | 内容                                                                                                                                                                                                                                                     |
|------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 对外只给裁剪视图 | `UpdateView` 是 tagged union，每个变体只携带该阶段前端渲染所需的字段                                                                                                                                                                                     |
| 凭据不外泄       | `Artifact`（url / sha256 / signature / size）、产物路径、`Policy`、`HistoryVersion` 全留在后端会话，不 `Serialize` 到视图、不导出 TS                                                                                                                     |
| 会话不导出       | `UpdateSession` 是后端内部类型（不 `Serialize`、不 ts-rs），只经 `view()` 投影                                                                                                                                                                           |
| 演进教训         | 早期对外返回**全量** `UpdateState`；早期 `UpdateSession` 有 `downloaded` / `total` / `error` / `error_kind` 四个字段 → "平铺 Option + 阶段载荷没进阶段 + 命中凭据被拆散又拼回"三重混乱。收敛后只剩 `status` / `info` / `severity` / `artifact` / `error` |
| 还删掉两个字段   | `current_version`（命令层可从 `package_info` 每次传入）、`downloaded_path`（磁盘可推导，见 §10.4）                                                                                                                                                       |

### 10.3 为什么进度与状态要分两条事件通道

现象：`invoke` 的响应与 `emit` 的事件是 **两个通道，顺序不保证**。若进度帧与终态混在一条通道，一个迟到的 `Downloading` 帧会把 UI 从终态（如 `Downloaded`）打回"下载中"，用户看到界面倒退。

结论： **拆通道即隔离陈旧帧**。

| 通道                           | 只载                                                                                            |
|--------------------------------|-------------------------------------------------------------------------------------------------|
| `rollcaller://update/view`     | 状态迁移帧（含进入 `Downloading` 一次）+ 各命令终态（同通道 emit 有序，迁移帧不可能迟到于终态） |
| `rollcaller://update/download` | `Downloading` 期的进度窄帧（不带 info / severity / 状态）                                       |

前端再加一道保险：进度帧 **只在当前状态是 `downloading` 时接受**，进出 `downloading` 一律重置进度槽。

**为什么进度连会话都不进**：进度是 **瞬时**数据（只在 `Downloading` 期有意义、终态必清零、跨命令无价值）；而错误是**持久**数据（要跨命令、跨窗口、经 `state()` 拉取）。二者混存会导致"清零职责散落"——所以进度外置到 `DownloadSlot` 原子槽（热路径每 chunk 只碰原子、不碰 session 锁），错误留在会话。

早期形态是命令上挂 `Channel<DownloadEvent>`（`Started` / `Progress` / `Finished`），该形态在"命令返回值即为唯一可靠锚点 + 广播喂全窗口"的目标下被替换。

### 10.4 为什么"下载只下载不解压"，以及"磁盘是产物唯一事实源"

| 决策                                                           | 理由                                                                                                    |
|----------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| download = 下载 + 整体验签，**不解压**（nsis / portable 一致） | 解压属安装语义；完整安装包保留到 install，避免"解压了但没装"的中间态                                    |
| install 时**再次**整体验签                                     | `Downloaded` 状态不代表产物仍有效；磁盘才是事实源                                                       |
| 就绪判据 = 磁盘事实                                            | 目标文件存在 + `size` 吻合 + 验签通过；不做 portable "已解压/已就绪"标记（标记会与磁盘漂移）            |
| 产物路径**不入会话**                                           | 路径可由凭据现推（`artifact.file_name()` + `paths::package`）；存起来反而制造"会话/磁盘不一致"的可能    |
| install 发现产物缺失 / 损坏 → `Error(Download)`                | 磁盘事实被推翻 → 要求重下。若落 `Error(Install)`，用户点"重试"会永远重试 install 而永远修不好（死循环） |

**布局演进的坑**：最初（方案 A）产物按版本建目录 `temp/update/downloads/<version>/`；后发现版本目录带来"换版本要清理旧目录、就绪探测要按目录寻址"的额外负担，于是推翻为 **平铺 +
文件名自带完整信息**——文件名（= url 最后一段）本身就是唯一标识，`size` 与验签即可判定就绪，无需版本目录。part 工作区仍独立在 `temp/downloads/`。

**`Artifact::file_name()` 去 panic**：早期签名是 `ok_or(...).unwrap()`，url 无文件名段即 panic。改为返回 `Option<String>`，`None` 语义 = "清单不合法"，由调用方在进入下载 / 就绪探测前报错。

### 10.5 为什么用 `.part` 落盘

做过的安全分析（结论直接决定实现）：

| 问                                             | 答                                                                 |
|------------------------------------------------|--------------------------------------------------------------------|
| 扩展名有意义吗                                 | 有——防"按扩展名自动 / 误触发执行"这一类被动风险                    |
| 对"本机已攻破的恶意进程主动执行任意文件"有用吗 | **无用**——内存、`.part`、分片三种形态等价无助（属杀软 / EDR 层面） |
| "写入磁盘的时间保密"可行吗                     | 在能监听文件系统的模型下**无解**                                   |
| 结论                                           | 放弃 2 MB 分片方案，采用 `.part`                                   |

`.part` 的性质：随机 uuid 命名（无信息量）、非可执行扩展名、顺序与内容不可按文件名推断；完整写盘
**且校验通过后**才 `rename` 为正式名。配合 §10.4 的"正式落点一定是已验证字节"，形成"磁盘上从不出现未验证的正式产物"。

### 10.6 为什么签名是"base64 (minisign 文本)"双层 —— 以及双重 base64 事故

| 项                | 内容                                                                                                                                                                                                                                              |
|-------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 约定              | `manifest.signature` 与公钥文件内容都是 **base64(minisign 文本)**；验签先 STANDARD base64 解外层，再交 `minisign-verify` 解内层（`.pub` 两行、`.sig` 四行）                                                                                       |
| 互操作            | `tauri-cli ≥ 2.11` 的 `.pub` / `.sig` **本身已是 base64(minisign 文本)**，可直接复制填入；旧版 CLI 产出明文 minisign 文本，才需手动 base64                                                                                                        |
| 事故 1            | 发布侧 `build_artifact` 曾对 `.sig` **再做一次** `b64encode` → 清单里是双重 base64 → 客户端 `Signature::decode` 报 `InvalidEncoding`（"Invalid encoding in minisign data"）                                                                       |
| 事故 1 的连锁误导 | 改了发布脚本后错误**仍然复现**——因为清单**缓存优先不过期**（`cache/update/{source}/{version}.json`），旧缓存仍在。排查多轮才定位到"必须删缓存"。**教训两条：① 别对已是 base64 的 `.sig` 再编码；② 变更清单契约后必须清理 `data/cache/update/`。** |
| 与密钥组的一致性  | 清单 `signature` 与后端嵌入的公钥必须来自**同一密钥组**；更换密钥组时旧签名的产物不再可验，因此格式上只保留 v2 一套（不双写 v1），避免"两套解码路径 + 两套签名预期"                                                                               |
| 空签名闸门        | 签名闸门在**两端**一致。客户端：`verify_artifact` / `verify_artifact_path` 要求签名必填（fail closed）。发布侧：一律要求签名非空——`manifest.read_sig_text` 对缺失 / 为空**直接报错**；`signer.sign_artifact` 签完若 `.sig` 为空即 `fail` 终止构建 |
| 编译期固化        | 公钥经 `include_str!` / 内联常量进入二进制，**改公钥文件必须重编译**；"改了文件却没生效"曾导致误判为算法问题                                                                                                                                      |

### 10.7 为什么"先打包重命名为最终名字，再依次签名"

不采用 bundler 构建期签名（`tauri.conf.json5` 的 `createUpdaterArtifacts = false`），改为两阶段：

```
阶段 1：全部产物（setup / portable / develop）由 packager 打包并重命名为最终名字
阶段 2：依次对它们调 tauri signer sign 手动签名，产出同名 .sig
```

理由： **让签名对象确定为"最终名字的最终字节"**，签名与重命名不再互相穿插。附带收益：`publisher` 侧按 `<产物名>.sig` 收集签名，与手动签名产物同名同目录，天然兼容（`collect_assets` / `build_payloads` 无需改动）。

代价：`packager` 不再拷贝 bundler 的 `.sig`（bundler 也不再生成；builder 每次构建前会清 bundle 目录，不会残留旧 `.sig`）。

### 10.8 为什么 `.sig` 不作为 Release 附件

只把 `.sig` 内容 **base64 嵌进清单**：省一次附件下载，且避免"附件签名与清单签名不一致"的可能。`build_ci.py` 的 artifact glob 仍上传 `.sig`，仅为在 job 之间传递到 `publish_ci.py`。

### 10.9 为什么 Develop 直更要换 exe 名（RustRover 占用 `rollcaller.exe`）

| 项   | 内容                                                                                                                                                                                                                                                                                                                                                |
|------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 现象 | RustRover 下 develop 自更新写 `target/debug/rollcaller.exe` 报 **os error 32**（`ERROR_SHARING_VIOLATION`，写打开被拒）；同一操作在终端 `cargo tauri dev` 下**每次成功**                                                                                                                                                                            |
| 机理 | Windows 加载器映射运行中镜像时以 `FILE_SHARE_READ \| FILE_SHARE_DELETE` 打开（**无 `FILE_SHARE_WRITE`**）→ 只要有**任一**进程持有该镜像句柄，写打开必失败，但**改名 / 删除仍允许**。`wait.pid` 只看发起更新的那个 app 自身，其它持有者（IDE debug 会话、符号读句柄、并发 cargo 构建、第二个实例、杀软）对它不可见——这正好解释"终端能成、IDE 不能成" |
| 解法 | develop 载荷 zip 内的文件名改为独立名 `rollcaller-update-from-develop.exe`（语义 = "由 develop 源装出来的那一个"）→ 写入新名，**不碰 IDE 映射的旧文件**；同时保留"等旧进程退出"（单实例锁 + `wait.pid`）                                                                                                                                            |
| 坑   | `launch.execution.path` 若仍指向旧 exe，会出现"**更新成功但仍启动旧 exe**"——必须指向新名                                                                                                                                                                                                                                                            |
| uuid | debug exe ≈ 39.8 MB，`cleanBeforeCopy = false` 不清目录 → uuid 会让每次更新在 `target/debug` 留一个 40 MB 文件无限累积；且 Rust 侧需扫目录找 exe + 额外清理逻辑。固定名唯一代价是"第二次更新写同名文件"，但第二次更新时由于不是 RustRover 主动运行的，因此不会被持有运行中镜像                                                                      |
| 收益 | `build_local` 那句"`rollcaller.exe` 被占用（tauri dev）请先停止"不再被"更新启动的实例"触发（它现在叫 develop 名），cargo 重新链接不再受阻                                                                                                                                                                                                           |

### 10.10 为什么 Develop 要用分离启动（`stayAlive: 0`）—— 0xC000013A 死亡

| 项               | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
|------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 现象             | 改名方案生效后，新进程正常启动并跑了约 7 s，随后 updater 日志 `launch stage failed: process exited with error: exit status 0xc000013a`。`0xC000013A` = `STATUS_CONTROL_C_EXIT`（控制台控制事件导致的终止），**不是**文件占用、不是普通崩溃                                                                                                                                                                                                                                                                      |
| 链路             | ① IDE 的 run session 给 app 一个 console；② app 以 `CREATE_NEW_PROCESS_GROUP \| DETACHED_PROCESS` spawn updater（updater 自身无 console）；③ 但 `runtime.headless = false` 使 updater 执行 `AttachConsole(ATTACH_PARENT_PROCESS)`，**主动附着回父进程的 console**（终端场景下这是有意的"复用父终端"设计）；④ `stayAlive = -1` 的新进程用默认创建标志，**继承 updater 的 console**（= IDE 那个）；⑤ app 退出 → IDE 收掉该 console → 附着进程收到 `CTRL_CLOSE_EVENT` → 新进程死亡。终端场景终端不消失，故历来正常 |
| 解法             | `stayAlive: 0` → Go updater 走 `NewDetachedProcAttr()` = `DETACHED_PROCESS \| CREATE_NO_WINDOW` → 新进程无 console → 免疫；且该分支**根本不读 `captureOutput`**（置 `false` 仅表意）                                                                                                                                                                                                                                                                                                                            |
| 代价             | 新进程 stdout 接 NUL 设备，且 app 文件日志层过滤级别是 WARN → 新实例的 INFO / DEBUG **完全无落点**。接受理由：① 捕获会把子进程输出以嵌套两层形态混进 updater 日志，不美观且本不该开；② 放宽 debug 文件日志级别会被 RBatis 的 SQL 冲爆；③ 直更演练结束后很快关掉 exe，不需要保活看输出                                                                                                                                                                                                                           |
| 后路             | `rollcaller-update-from-develop.exe` 是普通 debug 构建、不依赖 updater——想看完整输出直接手动运行它即可                                                                                                                                                                                                                                                                                                                                                                                                          |
| 被否决的替代方案 | `execution.mode = "interpreted"` + `interpreter = ["cmd","/c","start",""]` 给新进程自己的 console：技术上可行，但坑集中在"能不能跑对"——Go `CreateProcess` 转义与 cmd.exe 解析规则错配（`& ^ ( ) % !`）、`start` 的首个引号参数是窗口标题（须 `""`，引号行为一变就错位）、多一层 shell + 一个控制台窗 + updater 观测不到子进程；换来的只是"在窗口里看一次输出"，不值得                                                                                                                                           |

### 10.11 为什么 Portable 与 Develop 的 config 差这么多

差别全部源自 **target 的语义不同**：

| target   | 谁       | 语义                   | 后果                                                                                                             |
|----------|----------|------------------------|------------------------------------------------------------------------------------------------------------------|
| 程序目录 | Portable | 安装后的程序目录       | 整目录替换（`cleanBeforeCopy = true`）；用户数据在旁 `data/`，必须 `preserve`；整目录可备份 → 支持回滚           |
| 编译目录 | Develop  | `backend/target/debug` | **绝不能整目录清理**（其余中间产物必须保留）→ `cleanBeforeCopy = false`；整目录备份无意义且巨大 → 不备份、不回滚 |

配套约束： **config 与解压内容分居两个目录**（`temp/update/config` vs `temp/update/staging`），否则 updater 会把 config 当作 source 一起复制进 target。

**为什么 updater 的下载不复用 `download` 域**：落点语义不同（`cache/update/bin` 持久工具 vs `temp/update/packages` 临时产物），且 `download` 域把落点写死在自己的 `paths` 调用里。抽取 `download_to` 内核的方案 **已明确否决**（防回潮），改为在 install 域写一个"拉清单 + 下载 + 校验"的简单独立函数。

### 10.12 为什么错误合并成单一带数据枚举

| 阶段 | 形态                                                                                               | 问题                                                                              |
|------|----------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| 早期 | `UpdateErrorKind`（`Copy`、无载荷）+ 会话里 `error` 与 `error_kind` 两个字段                       | kind 信息与文案分离、易错配；`view.Error` 载荷是 `{message, retry}`，前端要自己拼 |
| 现状 | 单一 `UpdateError{Check(String) \| Download(String) \| Install(String)}`，tagged `{type, message}` | 变体身份 = "失败在哪一步" = "重试该调哪个命令"，类型层锁死配对                    |

原先拆两型的唯一理由是"retry 标签要 `Copy` + 视图形状"；合并后 kind 天然内嵌，代价只是投影时多一个 `match`——值得。

### 10.13 为什么编排层不持 `AppHandle`，而事件靠注入回调

| 决策                                                           | 理由                                                                                                                                                                                                             |
|----------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `service/update.rs` 全部函数纯 Rust、输入显式传参              | 可测；不把 Tauri 依赖渗进业务逻辑                                                                                                                                                                                |
| 事件由 `cmd` 层注入闭包（`on_view` / `on_progress`）           | 领域层与编排层都不知道"事件"存在，通道语义只写在命令层                                                                                                                                                           |
| 领域层只依赖 `paths` / `http_client` / `verify` 三个无状态叶子 | **反对的不是"直连"，而是"域依赖 app 级可变全局单例"**：`paths` 是无状态纯函数（保持域独立可测），`UpdaterState` 是 `manage` 注入、带 `Mutex`、被编排层独占的可变全局——域直连它就会焊死状态机、同模块出现两套规则 |

**曾经的教训**：`download` 域一度"特例化"为接收 `part_path` / `final_path` 参数（为了测试隔离）；后来测试改用独立数据根（见 §10.14），这个特例失去存在根基，于是回退为自包含（内部调 `paths::part()` / `paths::package(...)`）。同时期还收口了散落在编排层与下载域里的硬编码路径。

### 10.14 为什么测试用独立数据根（Test Mode）

领域函数统一"内部调 `paths`"后，测试隔离就成问题。解法不是注入点，而是 **在 `app_paths` 内分叉**：`detect_user_data_dir` 拆成 `#[cfg(test)]` / `#[cfg(not(test))]` 两版，测试构建的数据根 = `data/test/{uuid}/`（每次测试进程唯一，不自动清理以保留失败现场）。只有数据类目录（config / data / cache / temp / logs / webview2）被替换，`mode` 仍是 `Develop`、`resources` 与 `root_dir` 仍是真实路径。

收益：领域函数不必为测试设计注入点；`download` 的路径参数特例得以回退（§10.13）。 **不引入** `AppMode::Test` 变体（避免污染形态语义）。

### 10.15 为什么 CI 里 `BRANCH_NAME` 写死 `master`

`build.rs` 的 `GIT_BRANCH` 只喂 `config/app_info.rs`， **对更新链路无任何功能影响**。

CI 中 checkout 后是 **detached HEAD**，`git rev-parse --abbrev-ref HEAD` 恒返回 `"HEAD"`，故 `build_ci.py` 显式传 `BRANCH_NAME=master`。

### 10.16 为什么发布链路会长成现在这样

| 设计                                                   | 动因                                                                                                                                                                                                               |
|--------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `versions.json` 独立于 per-tag 清单                    | "坏版本检测"需要**历史每个版本**的 severity；枚举 GitHub tags 逐个下载清单有限流 / 国内通道问题 → 改为每次发布随手附一份全量索引。索引**不含任何 URL**（客户端凭版本号拼地址），因此双平台同名同内容               |
| severity 可回溯修正                                    | per-tag 清单发布即冻结；索引每次发版重新生成 → 下次发版时顺手把坏版本补标 `critical`；"修复版发布"与"补标坏版本"天然同拍                                                                                           |
| floor 而非 cap                                         | 桌面软件无 API 兼容包袱；用户嫌"更新太频繁"而非"变化太大"；被跳过的补丁是延迟聚合                                                                                                                                  |
| 拆"发布阶段"与"幅度门槛"两个维度                       | 旧 7 变体扁平枚举（`PatchStable` / `MinorPrerelease`…）语义耦合、组合爆炸；拆成 `level` + `channel` 两字段后，`validate` 可强制"关闭更新时通道归 Stable"防脏数据                                                   |
| 预发布分三条路径                                       | 三者风险完全不同（§5.3），不能用一个规则覆盖                                                                                                                                                                       |
| severity 豁免实现为"临时把门槛降到 `Patch`"            | 不必给 `decide` 增加"Skip 原因"，不破坏其纯 `Copy` 枚举形态，判定语义只写一次                                                                                                                                      |
| 移除 `force`                                           | `force` 与 severity 正交导致语义重复（`critical + force=false` vs `critical + force=true`）；简化为 **`critical` 即强制更新**（`level = Never` 也穿透）                                                            |
| 只做 v2、不双写 v1                                     | v1 清单格式已废弃：只保留 v2 一套结构与一条解码路径，避免双写与双份签名预期                                                                                                                                        |
| `release_local` 保留为统筹，拆 `build_*` / `publish_*` | 不做 `publish --develop` 多目标模式（很糟）。职责一分为二：**构建**（构建、打包、签名）vs **发布**（生成清单、发 Release）。`build_local` + `publish_local` 由 `release_local` 串起来                              |
| 本地清单缓存与产物目录名                               | 本地产物目录 = `release/Local/<core>+<branch>.<count>.<short_hash>/`（分支 `/` 替换为 `-`），同版本多目录取提交数最多者；清单 `version` 用 **core 版本号**（不带 `+build`），URL 段用 `v{core}`                    |
| `sync-mirrors` + CNB                                   | GitHub 是唯一数据源，CNB 是只读镜像；CNB 侧创建 Release 时 tag 必须已存在 → `publish_ci` **先发 GitHub、再轮询等 tag 同步（上限 300 s）、最后发 CNB**（tag 已有 Release 则 patch，否则 post）                      |
| CNB 附件三步上传                                       | 申请预签名 URL → 直接 PUT → 确认上传（无鉴权头直传，适合大文件）                                                                                                                                                   |
| CNB CLI 走 node 直调                                   | Windows 上 npm 安装的 `cnb` 是 `.cmd` shim，`subprocess` 无法直接执行，且 `cmd.exe /c` 会拆解含空格 / 引号的参数 → 统一 `node <cli.js>` 调用                                                                       |
| 版本文件临时改 + git 还原                              | 本地构建需要版本号进入 `tauri.conf.json5` / `Cargo.toml` 等 6 个文件，构建后必须还原（不提交）。因此 `build_local` 前置校验"这些文件工作区无未提交改动"，避免构建后的还原误伤用户改动（`git checkout -- <files>`） |
| 本地 release notes 用固定文本                          | `"本地测试发布 {目录名}"`，避免本地联调依赖 `RELEASE_NOTES.md` 的完整维护                                                                                                                                          |

### 10.17 为什么主包产物"签名必填"

主包产物（`nsis` / `portable` / `develop`）走组合校验入口时 **签名必填**：`signature` 为空直接拒绝，不做降级。设计上把"只验完整性"保留为 **独立原语** `verify_sha256`，组合入口本身不提供"跳过签名"的开关：

| 入口                                       | 语义                                                 | 使用者                                       |
|--------------------------------------------|------------------------------------------------------|----------------------------------------------|
| `verify_artifact` / `verify_artifact_path` | 签名必填 → sha256 → minisign（**全部通过才算通过**） | 主包产物（nsis / portable / develop）        |
| `verify_sha256`                            | 只验完整性（不涉及签名）                             | Go updater 更新器（扁平清单、仅发布 sha256） |

这样"签名的存在性"是一条 **不可选的常量**，而不是调用方可以漏填、漏判的字段。发布侧保持一致：`manifest.read_sig_text` 对缺失 / 为空的 `.sig` 直接报错，`signer.sign_artifact` 签完若 `.sig` 为空即 `fail` 终止构建——两端都不允许产出或接受无签名的更新产物。

## 11. 约束与遗留

### 11.1 后续改动不得违反的约定

1. 产物路径不入会话（事实源是磁盘，路径由凭据现推）。
2. 进度不入会话（瞬时数据进原子槽；持久数据才进会话）。
3. 领域层不依赖 `state` / `AppHandle`（只依赖 `paths` / `http_client` / `verify` 叶子）。
4. 错误变体身份 = 重试命令（新增失败位置时同步新增变体，不要退化为字符串）。
5. 进度与状态分两条通道（不要把进度塞回 view 通道）。
6. 签名不得缺席：客户端 `verify_artifact` / `verify_artifact_path` 对空签名一律拒绝（fail closed）；发布侧空签名必须报错，不得产出 `signature: ""` 的发布清单。
7. 状态机由后端推进、前端只镜像（不要在组件里推断阶段）。
8. 清单契约变更后必须清理 `data/cache/update/`（否则旧缓存让错误"永远复现"）。
9. `DEVELOP_UPDATE_BIN_NAME` 两端（Rust 常量 / `packager.py`）必须逐字符一致。
10. `paths.rs` 是布局唯一出口（不要在其他文件拼路径字符串）。

### 11.2 预留与未实现

| 项                             | 现状                                                                                                                             |
|--------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| 更新源选择                     | 由 `AppMode` 硬定（`Develop → Local`、`Install\|Portable → CNB`）；`UpdateSource::Github` 常量齐备但路径未接通                   |
| 用户策略设置                   | `current_policy()` 恒返回出厂默认（`Patch` + `Stable`），带 `TODO(设置存储)`；check 与 download 复核都吃这里，接入设置只需改一处 |
| 断点续传 / 多线程下载          | 未实现（GitHub 可行、CNB 不可，见 §6.5）                                                                                         |
| temp 清理规则                  | **未实现**；`paths.rs` 只声明"由 app 自管 temp 的清理规则兜底"                                                                   |
| 多窗口                         | 仅主窗口渲染更新入口并 autoCheck；设置窗口接入时需重审多实例订阅与 autoCheck 归属                                                |
| 更新器签名                     | Go updater 仅 sha256；其支持 minisign 后 `ensure_updater` 转为标准 Artifact 管线                                                 |
| 发布侧签名校验                 | 当前只校验"`.sig` 非空"，不做密码学验证（产出签名后在 Python 侧验一次，留待以后）                                                |
| `find_updater` 命名与行为      | 保留最大版本的行为正确；函数名与"发现即执行 / 清理"的副作用不够自表意（待改名）                                                  |
| `check` 的 `validate_manifest` | 索引 ↔ 清单一致性复判暂住 `check.rs`；其归宿是 `version.rs`（后期迁走）                                                          |
| 前端 `total = null` 文案       | 当前显示"总大小未知"；用户倾向用 `0` 代替（属后端语义调整，后置）                                                                |
| 清单自身的认证（预留加固）     | 与"签名必填"配套的后续加固项：让清单本身可验证。方案（索引同时携带清单的 hash 与签名）已定，实施排期待定                         |

### 11.3 关于 temp 清理规则的一点意见

现状是"临时目录只增不减"：`temp/update/packages` 允许他版本残留，`temp/update/staging` 与 `temp/update/config` 由 updater 完成后自行清理（实际未验证），`temp/downloads` 的 `.part` 只在取消 / 失败时删。

若按"启动日期被 3 整除时清 `temp`"实现，注意三点：

1. **清的范围应是 `temp` 整棵，而不是只清 update 子树**——否则规则名义上存在、实际只覆盖更新模块。
2. **`temp/update/packages` 被清是设计意图**（产物"安装即弃"、丢失后重下），但会产生一次"上次已下载、这次又要重下"的体验回退；可接受，因为判据本就是磁盘事实。
3. **别把 `cache/update/bin` 卷进来**——那是持久工具缓存，清了只是重下几十 MB，但语义上不属于 temp。

替代方案（供参考，不比 `%3` 更优也不更差）：按大小上限 + LRU（超出阈值时删最旧的 `packages` 条目、`.part` 一律可删）。优点是"不依赖启动次数"、行为更可预期；缺点是需要维护时间戳 / 大小索引。若只想要低成本方案，`%3` 足够。

## 12. 附录

### 12.1 清单结构（`latest-{github|cnb|develop}.json`）

```jsonc
{
  "version": "0.8.0",                    // semver
  "releaseNotes": "…",
  "publishDate": "2026-09-06T08:00:00Z", // ISO 8601
  "severity": "normal",                  // normal | important | critical（缺省 normal）
  "platforms": {
    "windows": {
      "x86_64": {
        "nsis":     { "url": "…", "sha256": "…", "signature": "…", "size": 123 },
        "portable": { "url": "…", "sha256": "…", "signature": "…", "size": 123 },
        "develop":  { "url": "…", "sha256": "…", "signature": "…", "size": 123 }
      },
      "arm64": { "nsis": {}, "portable": {} }
    }
  }
}
```

schema 见仓库 `docs/schema/latest-manifest.schema.json`；构造代码 `scripts/common/manifest.py`。`nsis` / `portable` / `develop` 三个槽可缺省（缺省 = 该形态无产物）。

`Artifact` 的落点命名规则：`file_name()` = url 最后一段；下载器与就绪探测都按它寻址，所以 **发布侧产物名必须自带版本 / 平台 / 架构**。

### 12.2 版本索引（`versions.json`，裸数组）

```json
[
    {
        "version": "0.8.0",
        "severity": "normal"
    }
]
```

- 仓库源 `resources/update/versions.json` 是 **发布期唯一标定 severity 的地方**，由 `scripts/update_versions_index.py <版本> [--severity …]` 维护（写入后按主/次/补丁倒序重排）；
- 发布时随 Release 附一份（双平台同名同内容）；
- 客户端每次检查都拉取，用于在 `(current, latest]` 区间挑"最高可安装版本"；
- `severity` 缺失 / 非法按 `normal` 兜底（兼容老索引）。

### 12.3 发布链路

```
本地：release_local.py <版本>
        ├─ build_local.py   ：update_version.sync（临时改 6 个版本文件）→ 构建 → 打包重命名
        │                     → 依次 tauri signer sign → git 还原版本文件
        └─ publish_local.py ：生成 latest-develop.json + versions.json（产物 URL 指向 localhost:14652）
      → local_update_source_server.py <版本>（--rate 限速产物直链）
      → 应用以 Develop 形态（UpdateSource::Local）联调

CI：push tag v* / workflow_dispatch
      validate（build_ci.ci_version：rc 及以上，禁 alpha/beta）
      → build（矩阵 x86_64-pc-windows-msvc / aarch64-pc-windows-msvc）
          build_ci.py build --target <t>：VERSION + BRANCH_NAME=master 注入 → 构建 → 打包 → 签名
          upload-artifact（2 setup + 2 portable + 各自 .sig）
      → release
          publish_ci.py：提取版本 → 从 RELEASE_NOTES.md 抽章节 → 校验 4 产物 + 4 签名
            → 生成 latest-github.json / latest-cnb.json / versions.json
            → GitHub Release（gh cli）
            → 等 sync-mirrors 把 tag 同步到 CNB（轮询 git ls-remote，上限 300 s）
            → CNB Release（cnb cli：patch 或 post）→ 三步上传附件
```

版本号格式约束：

| 环节        | 约束                                                                                                                                            |
|-------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| 本地构建    | 不允许版本号自带 `+`（构建信息由脚本追加：`<branch>.<count>.<short_hash>`）                                                                     |
| CI 发布     | `min_level = "rc"`（放行 rc 及以上，禁 alpha / beta）                                                                                           |
| 打 tag      | `scripts/tag_release.py <版本>`：要求"必须在 `master` / `main` 分支 + `versions.json` 已标定该版本 + 本地无同名 tag"，然后 `git tag -a v{版本}` |
| 清单 / 索引 | 均为 core 版本号（不带 `v`、不带 `+build`）；tag 带 `v`                                                                                         |

### 12.5 验证方式速查

```shell
cd backend && cargo check --lib                       # 编译
cd backend && cargo test --lib                        # 单测（download 含 mock 服务器集成测试）
cd backend && cargo test export_bindings_             # 重新导出前端 TS 类型
cd backend && cargo test --lib service::update::version   # 只测决策表

```

验证重点：状态机迁移（含取消与重试路径）、就绪锚点（产物存在 / 损坏 / 缺失三种）、双通道事件语义（终态在 view 通道、进度帧在 download 通道）、签名互操作（`verify::interop_with_tauri_signer`）、本地源限速精度与 `Content-Length`。
