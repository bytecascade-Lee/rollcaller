# RELEASE_NOTES.md 书写规范

> 位置：`docs/standards/RELEASE_NOTES_STANDARD.md`，适用对象为仓库根目录的 `RELEASE_NOTES.md`。
> 面向开发者的变更记录见 `docs/standards/CHANGELOG_STANDARD.md`。
> **本文档规定的标题格式由 CI 强制校验**，不符合将直接导致发布流程在 `prepare` 阶段失败。

---

## 一、定位

**RELEASE_NOTES 面向最终用户**，回答的问题是：**这个版本对我来说有什么变化？**

- 语言通俗，不出现代码级术语
- 聚焦用户可感知的变化，而非实现细节
- 帮助用户决定是否升级，以及升级需要注意什么

---

## 二、版本号与标题

### 标题格式

````text
## 0.8.2 {#v0-8-2}
````

- 版本号遵循[语义化版本](https://semver.org/lang/zh-CN/)：`主版本号.次版本号.修订号`，预发布版本附加 `-alpha.x` / `-beta.x` / `-rc.x`
- 标题中的版本号**不带 `v` 前缀**，`v` 只出现在 git tag 与锚点上
- 锚点 = `v` + 版本号，`.` 与 `-` 一律替换为 `-`（`0.3.0-rc.1` → `{#v0-3-0-rc-1}`），以区别于 `CHANGELOG.md` 的锚点

### CI 约束（硬性）

发布流水线的 `prepare` 阶段从本文件提取待发布版本的章节，实现见 `scripts/release/release_notes.py`。以下三条任一不满足即失败：

| 约束 | 说明 |
|:--|:--|
| **存在** | 必须能匹配到 `^## <版本号>` 开头的标题行 |
| **唯一** | 同一版本号只允许出现一个章节，重复即报错 |
| **非空** | 标题行到下一个 `##` 之间必须有内容 |

- **禁止写成 `## [0.8.2]`**：方括号会导致标题匹配不到，`prepare` 报「未找到标题」
- 标题行允许带锚点后缀，这是唯一被允许的附加内容
- 章节末尾与下一章之间的 `---` 分隔线不计入章节内容
- 草稿发布（`--draft`）跳过该校验

### 版本排序

**按时间倒序排列**，最新版本在最上方。

### 补丁版本

补丁版本（修订号递增，如 1.0.0 → 1.0.1）是正式发行版本：

- 每个补丁版本**单独成章**，不合并或汇总到其他版本
- 下一个次版本或主版本发布时，补丁版本的历史记录**保留不变**
- 章节结构可精简（省略「版本亮点」「新增功能」「体验改进」），但**「重要修复」与「升级注意」必须保留**

### 预发布版本

- 预发布版本（RC / Alpha / Beta）简要记录，篇幅不超过正式版的一半
- 第一行须说明「本版本包含上一个预发布版本的全部内容」
- **正式版本**：汇总其全部预发布版本的用户可见变化，写成完整章节

## 三、顶部目录

文件开头固定为一段目录，逐条列出所有版本，顺序与正文章节一致（倒序）：

````text
## 目录

- [0.8.2](#v0-8-2) — 批量导入可选工作表、支持 .xls，更新检查不再打扰
- [0.8.1](#v0-8-1) — 验证自动更新链路、命令行诊断参数
````

- 每行格式：`- [<版本号>](#<锚点>) — <一句话摘要>`
- 摘要用**中文**一句话，概括本版本最值得用户关注的变化
- 新增版本时，同步在目录列表**顶部**插入一行
- 目录不参与 CI 校验，但缺失属文档缺陷

## 四、章节结构

### 主版本 / 次版本

按以下顺序包含对应章节：

| 章节     | 是否必须             | 说明                                             |
|:---------|:---------------------|:-------------------------------------------------|
| 版本亮点 | 是                   | 1-2 句概括本次更新最值得关注的内容，点明价值     |
| 新增功能 | 否（有则写）         | 用户能直接使用的新功能，按模块分点描述           |
| 体验改进 | 否（有则写）         | 性能提升、交互优化、界面打磨，不含技术细节       |
| 重要修复 | 否（有则写）         | 只列用户会遇到且影响使用的问题，一般 3-6 条      |
| 升级注意 | 有则写，无则写「暂无」 | 破坏性变更、数据库迁移、配置变更，必须醒目     |
| 已知问题 | 有则写，无则写「暂无」 | 当前版本已知但尚未修复的问题及临时应对方案     |

> 某版本没有新增功能或修复时可跳过对应章节，但「版本亮点」与「升级注意」仍需保留。

### 补丁版本

补丁版本的章节结构可精简，省略「版本亮点」「新增功能」「体验改进」，但**「重要修复」与「升级注意」必须保留**：

| 章节     | 是否必须              | 说明                                       |
|:---------|:----------------------|:-------------------------------------------|
| 重要修复 | 是                    | 本次补丁修复的问题，按影响范围分点描述     |
| 升级注意 | 有则写，无则写「暂无」 | 破坏性变更、数据库迁移、配置变更           |
| 已知问题 | 有则写，无则写「暂无」 | 当前版本已知但尚未修复的问题及临时应对方案 |

### 预发布版本

预发布版本可简化为以下格式：

````markdown
## x.y.z-rc.n {#vx-y-z-rc-n}

本版本包含 x.y.z-rc.(n-1) 的全部内容，以下为增量变更：

- **新增**：简要列出新增的用户可见功能
- **改进**：简要列出改进点
- **修复**：简要列出修复的问题

> ⚠️ 如有破坏性变更或数据库迁移，必须在此醒目提示。
````

## 五、书写规范

### 语言风格

- 使用中文，通俗但克制：面向最终用户，可读性优先，不追求术语精确
- 用主动语态（「支持了…」「新增了…」），不用被动语态
- 不使用「我们」，直接陈述事实
- 不使用网络用语、感叹号与营销式夸张（「史上最强」「彻底解决」一类）
- 涉及技术概念时，用用户能理解的说法替代（「数据库升级」而不是「schema migration」）

### 条目书写

- 每个条目以 `-` 开头
- 描述独立成句，以动词开头：新增、优化、修复、调整、移除
- 不出现代码、文件名、函数名、类名
- 不出现 issue 编号（归 `CHANGELOG.md` 管理）
- 涉及具体功能时，用界面上的实际文案称呼它

### 正反例

| 错误写法                                               | 正确写法                                                 |
|:-------------------------------------------------------|:---------------------------------------------------------|
| 修复了 `EditRecord` 组件未选择更新项时按钮仍启用的问题 | 修复编辑考勤记录时未做任何修改但「确定」按钮仍可点击的问题 |
| 新增 `AttendanceStatusStore.svelte.ts` 全局状态管理    | 出勤状态改为数据库统一管理，为后续自定义状态打下基础     |
| 修复状态 ID 从 0 起始改为 1 起始导致的显示异常         | 修复部分场景下学生考勤状态显示错误的问题                 |

## 六、示例

````markdown
# 版本发布说明

> 如有问题或建议，欢迎在 [Issue](https://github.com/bytecascade-Lee/rollcaller/issues) 区提出。

---

## 目录

- [1.0.1](#v1-0-1) — 修复特定场景下崩溃的问题
- [1.0.0](#v1-0-0) — 首个正式版本

---

## 1.0.1 {#v1-0-1}

### 重要修复

- 修复特定情况下崩溃的问题。
- 修复某功能在特定场景下失效的问题。

### 升级注意

暂无。

---

## 1.0.0 {#v1-0-0}

### 版本亮点

一句话说明这个版本最值得关注的变化。

### 新增功能

- **功能模块**：功能描述，说明用户能做什么。
- **另一功能**：功能描述。

### 体验改进

- 优化了某流程，现在操作更顺畅。
- 界面某区域重新设计，信息更清晰。

### 重要修复

- 修复特定情况下崩溃的问题。
- 修复某功能在特定场景下失效的问题。

### 升级注意

本次包含数据库变更，升级前请备份数据。

### 已知问题

暂无。
````

## 七、检查清单

发布前逐项确认：

- [ ] 标题格式为 `## <版本号> {#v<锚点>}`，版本号不带 `v` 前缀，且与计划发布的 tag 一致
- [ ] 该版本号在文件中**只有一个**章节，且章节非空（CI 会校验这三条）
- [ ] 顶部目录已新增对应行，链接可跳转到本章节
- [ ] 所有预发布版本的内容已合并到对应的正式版本
- [ ] 主版本 / 次版本包含「版本亮点」章节
- [ ] 补丁版本包含「重要修复」与「升级注意」章节
- [ ] 没有出现代码、文件名、函数名
- [ ] 没有出现 issue 编号
- [ ] 「升级注意」醒目且完整
- [ ] 版本按时间倒序排列
- [ ] 链接（如 Issue 入口）可正常访问
